# Комплект программных документов РАГРАФ (ЕСПД, ГОСТ 19)

**Обозначение изделия:** 00000-00000.
**Изделие:** РАГРАФ — фреймворк инструментов для построения платформ проверяемого управления.
**Дата:** 2026-09-04.

---

## Зачем отдельный комплект

Изделие поставляется двумя частями:

```
комплект РАГРАФ (фреймворк)  +  папка платформы (отраслевая настройка)
```

Такое деление не оформительское, оно отражает устройство продукта. Ядро — язык регламентов, исполнитель, шлюз событий, хранилище, интерфейс — доменно-нейтрально и не содержит сведений об отрасли. Отрасль задаётся настройкой: набором датасетов и регламентов. Платформа «АРХИ» для строительства — первая такая настройка, и отраслевого кода в ней около 4 % (`docs/ARCHI-CONSTRUCTION/README.md`).

Пока комплект был один, платформенные документы вынужденно описывали и ядро, и отрасль вперемешку. Разделение снимает три проблемы: одно и то же не пишется дважды; при появлении второй платформы не приходится копировать комплект целиком; и при передаче платформы заказчику видно, что именно передаётся, а что лицензируется.

## Обозначения

| Изделие | Обозначение | Каталог |
|---|---|---|
| РАГРАФ — фреймворк | **00000-00000-XX** | `docs/RAGRAF/GOST-19/` |
| Платформа АРХИ — строительство | **11710-11710-XX** | `docs/ARCHI-CONSTRUCTION/GOST-19/` |
| последующие платформы | по коду организации-разработчика | своя папка |

Виды документов — по ГОСТ 19.101-77, структура обозначения — по ГОСТ 19.103-77: код организации-разработчика, регистрационный номер, номер документа по виду. Спецификация по ГОСТ 19.202-78 обозначается обозначением самой программы, без кода вида.

**Почему нули.** Регистрационный номер фреймворку не присваивался: РАГРАФ разрабатывается вне организации, чей код (11710) носит платформа АРХИ. Ставить чужой код организации-разработчика на фреймворк неверно — это отнесло бы права к организации, которая его не разрабатывала. Нули означают «обозначение не присвоено» и заменяются, когда и если регистрация состоится.

Правило одно: **платформенный документ не повторяет фреймворковый, а ссылается на него.**

## Учебник как структурная и идейная основа

Комплект строится **на структуре учебника** `docs/BOOK/`, а не на произвольном порядке разделов. Учебник писался для людей с аналитическим складом ума, не для программистов, и его порядок изложения проверен на читателе. Формальный документ, изложенный в том же порядке, читается, а не только сдаётся.

**Что переносится.**

| Из учебника | В документы комплекта |
|---|---|
| Порядок: задача и критерий → ядро из пяти узлов → пресеты и время → запуск и проверка → замкнутый контур и двойник | порядок разделов «Описания языка» 00000-00000-35 |
| «Регламент — это задача с критерием решённости» | раздел «Общие сведения о языке»: назначение и характеристика |
| Три глагола: измерить → оценить → действовать | объяснение состава узлов; читатель получает карту до перечня |
| «Пять узлов, а не зоопарк из полусотни значков» | обоснование выбора элементов языка |
| ⚠ грабли каждой главы | раздел «Средства отладки»: таблица типовых ошибок и способов исправления |
| Учебные регламенты домена `tutorial` | приложение «Примеры», от простого к сложному |
| Канва главы: зачем → один новый термин → открой и увидь → сценарий → практика | построение практикума в руководстве программиста 00000-00000-33 |

**Что не переносится.** Обращение на «ты», значки, интонация разговора с учеником, оценочные формулировки. Программный документ сохраняет деловой регистр: не «запомни пять — и ты уже можешь», а «язык содержит пять основных типов узлов». Переносится порядок мысли и способ объяснения, а не голос.

**Почему так.** Стандарт задаёт, какие сведения обязаны быть в документе, но не запрещает располагать их так, чтобы документ можно было прочесть подряд. Перечень элементов языка, выданный до объяснения, зачем эти элементы нужны, формально соответствует ГОСТ и практически бесполезен.
