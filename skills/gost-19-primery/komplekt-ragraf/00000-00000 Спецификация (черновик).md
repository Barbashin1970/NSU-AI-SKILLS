### 4.1. Комплекс 00000-00000 01 «Язык регламентов и интерпретатор»

**Назначение.** Детерминированное исполнение регламента, описанного графом Flow DSL из девяти типов узлов — вход, порог, сравнение, формула, развилка, выход, проверка ограничения, датчик, время (`backend/app/schemas/domain.py:342`). Комплекс разрешает показания на входные узлы, вычисляет узлы, обходит граф вперёд от сработавших источников и формирует вердикт с пошаговой трассой (`backend/app/services/flow_executor.py:126`).

**Входные данные.** Граф `RuleDSL`, объект `Regulation`, перечень показаний `SensorReading` и отметка «текущего времени» для узлов времени и временных функций (`flow_executor.py:67`, `flow_executor.py:131`).

**Выходные данные.** Объект `ExecutionResult`: уровень критичности 0–3, рекомендация, перечни сработавших узлов и связей, трасса по узлам и разрешённые входы (`flow_executor.py:102`, `flow_executor.py:90`).

**Связи.** Зависит от комплекса 03 (граф и регламент читаются из хранилища) и от комплекса 04 (формальные ограничения для узла проверки, `flow_executor.py:1005`). От него зависят: 02 — применитель событий вызывает интерпретатор на каждом цикле; 05 — статический анализ переиспользует разбор формул (`backend/app/services/validator.py:21`); 06 — метрики и критерии решённости считаются по результату прогона; 07 — доставка вердиктов; 08 — прогон на тестовых данных в редакторе.

**Ограничения.** Вычислитель формул работает по белому списку узлов синтаксического дерева, без вызова `eval`/`exec` и без обращения к атрибутам и подпискам (`backend/app/services/formula_eval.py:38`, `formula_eval.py:141`); показатель степени ограничен значением 1024 (`formula_eval.py:462`). Действует трёхзначная логика Клини: при отсутствии данных результат «неизвестно» — узел формулы **не срабатывает**, вердикт не выдаётся, и в трассе проставляется отметка «нет данных» (`formula_eval.py:480`, `flow_executor.py:849`). Узел проверки ограничения без ссылки на ограничение, с неизвестной ссылкой либо при отсутствии значения пропускается как выполненный (`flow_executor.py:1015`).

## 6. Порядок проверки состава при приёмке (дополнительный раздел)

Раздел введён сверх ГОСТ 19.202-78 по той же причине, что и раздел 5: перечень составных частей, который нельзя проверить командой, при приёмке не проверяется вовсе. Ниже — порядок, воспроизводимый проверяющим самостоятельно, **без запуска изделия** для шагов 1–5.

### 6.1. Шаг 1. Фиксация проверяемой редакции

```
git rev-parse --short HEAD      → должно совпасть с коммитом, указанным в шапке
git status --short              → пустой вывод: неучтённых и изменённых файлов нет
git ls-files | wc -l            → 987
```

Если рабочее дерево не чисто либо коммит не совпадает с указанным в шапке, дальнейшая проверка проводится с занесением расхождения в протокол: показатели спецификации относятся к другой редакции изделия.

### 6.2. Шаг 2. Проверка состава по разделам 2 и 3

| Показатель | Команда | Значение по спецификации |
|---|---|---|
| Модулей серверной части | `find backend/app -name '*.py' -not -path '*__pycache__*' \| wc -l` | 110 |
| Строк серверной части | та же команда с `-exec cat {} + \| wc -l` | 43 804 |
| Модулей клиентской части | `find frontend/src \( -name '*.ts' -o -name '*.tsx' \) \| wc -l` | 122 |
| Маршрутизаторов | `grep -c 'include_router' backend/app/main.py` | 31 |
| Обработчиков запросов | `grep -rh '^@router\.' backend/app/api/*.py \| wc -l` | 234 |
| Наборов приёмочных проверок | `ls backend/tests/test_*.py \| wc -l` | 74 |
| Объявлений проверок | `grep -rhE '^[[:space:]]*(async )?def test_' backend/tests/*.py \| wc -l` | 615 |
| Собранных вариантов проверок | `python3 -m pytest --collect-only -q` из каталога `backend` | 772 |

**О двух числах проверок.** 615 — число объявленных тестовых функций, 772 — число собранных вариантов с учётом раскрытия параметризации. Оба верны и относятся к разному; разница 157 приходится на шесть наборов. В протокол заносятся оба с указанием способа получения. Сбор без исполнения рабочие данные не изменяет — проверено сличением состояния каталога данных до и после.

### 6.3. Шаг 3. Проверка поставляемых данных

| Показатель | Команда | Значение |

**Рабочая база при приёмке эталоном не является** и в состав поставки не входит. Если проверяющему требуется установить её содержимое, файл базы копируется и **копия** открывается в режиме только для чтения; открывать рабочий файл на запись при приёмке недопустимо.

### 6.6. Шаг 6. Проверка работоспособности состава

Проверяющий запускает `start.command` (macOS, Linux) либо `start.bat` (Windows) без ключей и выбирает пункт 2 «Приёмочные испытания, ядро» либо пункт 3 «Приёмочные испытания, полный комплект». Прямой вызов: `python3 scripts/acceptance_tests.py --full`.

| Ключ | Действие |
|---|---|
| без ключей либо `--quick` | быстрый набор: 22 набора из 74 |
| `--full` | полный набор: 74 набора, 772 проверки |
| `--no-frontend` | без проверок клиентской части |

Коды возврата: **0** — все проверки пройдены, **1** — есть непройденные, **2** — прогон выполнить не удалось (нет окружения либо не найден каталог проверок). Код 2 несоответствием состава не является — он означает, что проверка не состоялась.

По итогам прогона формируются `reports/protokol-ispytaniy.html` и `reports/akt-sdachi-priemki.html`. В системе контроля версий они не хранятся.

**Ограничение, которое проверяющий обязан учитывать:** проверки клиентской части **пропускаются без отметки об отказе**, если её зависимости не установлены. Пустой результат по клиентской части и успешный код возврата совместимы; факт выполнения проверок клиентской части устанавливается по протоколу, а не по коду возврата.

### 6.7. Шаг 7. Проверка двух сборок клиентской части

```
cd frontend && npm ci && npm run build          → каталог dist
                        npm run build:landing   → каталог dist-landing
                        npx tsc --noEmit        → контроль типов, без ошибок
                        npm run lint            → статический контроль
```

Комплекс 00000-00000 08 выпускается двумя сборками; проверка одной полноту состава не подтверждает.

### 6.8. Что считать несоответствием

| Наблюдение | Как трактуется |
|---|---|
| Показатель не совпал с приведённым в разделах 2, 3, 6 | не несоответствие само по себе: спецификация подлежит переизданию по п. 5.9. Несоответствием является **отсутствующая либо не объявленная составная часть** |
| Ссылка `файл:строка` указывает на несуществующий файл | несоответствие состава |
| Ссылка указывает на существующий файл, но иную строку | устаревание спецификации; заносится в протокол, переизданием устраняется |
| Прогон вернул код 1 | несоответствие: изделие не проходит собственные приёмочные проверки |
| Прогон вернул код 2 | проверка не состоялась; повторяется после установки окружения |
| Рабочая база содержит записи сверх реестра поставки | не несоответствие: рабочая база в поставку не входит (п. 5.6) |

### 6.9. Форма протокола проверки состава

Протокол проверки состава оформляется приложением к протоколу приёмочных испытаний и содержит: проверяемый коммит и состояние рабочего дерева; таблицу «показатель — команда — значение по спецификации — фактическое значение — вывод» по шагам 2–5; результат прогона с кодом возврата и числом пройденных проверок; перечень выявленных расхождений с разделением на несоответствия состава и устаревания спецификации.
