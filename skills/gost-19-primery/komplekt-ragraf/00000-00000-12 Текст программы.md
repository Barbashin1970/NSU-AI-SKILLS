## 1. Способ прочтения стандарта (дополнительный раздел)

ГОСТ 19.401-78 определяет текст программы как символическую запись на исходном языке и писался для эпохи, когда текст программы распечатывался и передавался листингом.

Полный листинг изделия составил бы **около 1 690 страниц** (101 404 строки исходного текста при 60 строках на страницу). Такой документ не читается, устаревает при первом же изменении и не решает ни одной задачи, ради которой текст программы затребован.

Поэтому настоящий документ является **описью**: он устанавливает, из чего состоит исходный текст, в каком порядке из него собирается поставка, какими версиями зависимостей она определена и по каким контрольным суммам проверяется её тождественность. Сам текст передаётся репозиторием.

Такое прочтение соответствует формулировке заказчика — «комплект исходных кодов и материалов, необходимых для сборки, развёртывания и воспроизведения поставки» — и зафиксировано в плане комплекта (`PLAN-KOMPLEKTA.md`, раздел 2).

Требование листинга сохраняется в одном случае — при государственной регистрации программы для ЭВМ. Оно закрыто разделом 10 и приложением В: депонируются не все 1 690 страниц, а отобранные фрагменты, идентифицирующие программу.

## 5. Порядок сборки

### 5.1. Сборка образа контейнера — основной путь поставки

Двухэтапная, описана файлом `Dockerfile` (129 строк).

**Этап 1 — сборка клиентской части** на образе `node:20-alpine` (`Dockerfile:14`):

```
COPY frontend/package.json frontend/package-lock.json* ./     # Dockerfile:20
RUN npm ci --no-audit --no-fund || npm install --no-audit --no-fund   # :21
COPY frontend/ ./                                             # :24
RUN npm run build                                             # :25
```

**Этап 2 — исполняющая среда** на образе `python:3.12-slim` (`Dockerfile:30`):

```
COPY backend/requirements.txt /srv/backend/requirements.txt   # :48
RUN pip install --no-cache-dir --upgrade pip && …             # :49
COPY backend/app /srv/backend/app                             # :53
COPY backend/data/fixtures /srv/backend/data/fixtures         # :62
COPY backend/data/demo_documents …                            # :68
COPY backend/data/knowledge_seed …                            # :78
COPY installer /srv/installer                                 # :100
COPY --from=frontend-builder /app/dist /srv/frontend_dist     # :103
COPY start.sh /srv/start.sh                                   # :106
EXPOSE 8080                                                   # :127
CMD ["/srv/start.sh"]                                         # :129
```

Существенно: **рабочие файлы баз данных в образ не копируются.** В него входят только неизменяемые данные — эталонный корпус регламентов, начальное наполнение графа знаний и демонстрационный документ. Первичное заполнение тома выполняет пусковой файл при запуске.

### 5.2. Локальная сборка

```
cd backend  && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cd frontend && npm ci && npm run build            # каталог dist
```

### 5.3. Сборка витрины

```
cd frontend && npm run build:landing              # каталог dist-landing
```

Отдельная конфигурация `frontend/vite.landing.config.ts` собирает только посадочные страницы, без клиента программного интерфейса и разделов рабочего места. Команда сборки переименовывает `index-landing.html` в `index.html` (`frontend/package.json:10`).

**Каталог `frontend/dist-landing` учтён в системе контроля версий** — 27 файлов, 47,3 Мбайт. Это отличает его от `frontend/dist`, который не учитывается. Следствие: при изменении посадочных страниц или входящих в них статических ресурсов сборку витрины необходимо выполнить и зафиксировать вместе с исходным текстом, иначе учтённая сборка разойдётся с источником.

| Величина | Значение | Команда |

Отдельные контрольные суммы файлов приведены в приложении Б для случая, когда изделие передаётся без системы контроля версий.

## 8. Условия воспроизводимости и их ограничения

### 8.1. Что воспроизводится строго

- Состав исходного текста — хешем дерева.
- Версии клиентских пакетов — файлом блокировки при установке командой `npm ci`.
- Исполняющая среда контейнера — образом `python:3.12-slim` и образом `node:20-alpine`.

### 8.2. Что воспроизводится нестрого

- **Серверные зависимости.** Файла блокировки для серверной части нет, контрольных сумм пакетов (`--hash`) в перечне нет. Шестнадцать пакетов закреплены точно, но привлечённые ими 85 — нет; установка на разные даты может дать разные их версии.
- **Локальная установка клиентской части.** Пусковые файлы разработчика применяют `npm install`, а не `npm ci`; фиксация файлом блокировки при этом обходится. В образе контейнера применяется `npm ci` с откатом на `npm install` при отказе (`Dockerfile:21`).
- **Нижняя граница версии интерпретатора Python** объявлена четырьмя разными значениями в разных файлах (3.10, 3.11, 3.12, 3.13); фактический предел, определяемый применёнными конструкциями языка, — 3.10.

### 8.3. Известные расхождения состава

- `pyshacl` объявлен зависимостью, но в исходном тексте не импортируется ни разу. Удалению не подлежит без правки пусковых файлов: они проверяют его наличие контрольным импортом и по результату решают, устанавливать ли зависимости заново.
- `@dnd-kit/core` и `@dnd-kit/sortable` объявлены в клиентской части, не импортируются нигде и порождают пустой фрагмент выходного кода.

Оба расхождения записаны в `docs/BACKLOG.md` и в раздел 5.4 спецификации 00000-00000.

## 9. Порядок проверки воспроизводимости при приёмке

1. **Тождество состава.** `git rev-parse 'HEAD^{tree}'` — сверить с шапкой настоящего документа. При передаче без системы контроля версий — сверить контрольные суммы приложения Б.
2. **Сборка образа.** `docker build -t ragraf .` — должна завершиться без ошибок; проверяется наличие в образе каталогов `fixtures`, `knowledge_seed`, `demo_documents` и собранной клиентской части.
3. **Сборка клиентской части из чистого состояния.** `rm -rf frontend/node_modules && cd frontend && npm ci && npm run build` — воспроизводит каталог `dist`.
4. **Сборка витрины.** `npm run build:landing` — результат сравнивается с учтённым каталогом `frontend/dist-landing`; расхождение означает, что сборка не была зафиксирована вместе с источником.
5. **Контроль типов и статический контроль.** `npx tsc --noEmit` и `npm run lint` — без ошибок.
6. **Приёмочный прогон.** Порядок — раздел 6 спецификации 00000-00000 и программа испытаний 00000-00000-51.

Отобранное намеренно не содержит отраслевых модулей: они относятся к комплекту платформы 11710-11710 и в состав регистрируемого изделия не входят.

### 10.4. Оформление депонируемых материалов

- Титульный лист: название программы, правообладатель, год.
- Сквозная нумерация страниц.
- Реферат — отдельным листом, по тексту п. 10.1.
- Кодировка распечатки — UTF-8; строки длиннее ширины страницы переносить с сохранением отступов.

### 10.5. Что проверить перед подачей

1. Сверить пределы объёма с текущей редакцией регламента (см. оговорку выше).
2. Убедиться, что редакция изделия, с которой снят листинг, совпадает с указанной в шапке настоящего документа: хеш дерева `de86c5c`.
3. Убедиться, что в депонируемые фрагменты не попали ключи доступа и адреса внешних узлов. Отобранные в приложении В файлы их не содержат — ключи хранятся только в файле окружения, который в систему контроля версий не попадал ни разу.
4. Сверить наименование изделия с наименованием в комплекте документации: расхождение названия в заявке и в документах затрудняет подтверждение прав.

## ПРИЛОЖЕНИЕ В. Состав депонируемых материалов

Готовый к подаче документ — `docs/RAGRAF/FIPS/Программа ЭВМ. Листинг кода.md`. Он собран по образцу оформления, принятому при регистрации программного фреймворка «Сигма»: титульный лист с наименованием, числом листов, автором и правообладателем, далее подряд «Листинг N — Файл …» с полным текстом файла.

Отобраны пять файлов доменно-нейтрального ядра — существо решения: исполнение регламента, вычисление выражений, проверка графа правила, анализ свода и вероятностная оценка.

| № | Файл | Строк | Листов | Что идентифицирует |
|---|---|---|---|---|
| 1 | `backend/app/services/flow_executor.py` | 1 041 | 23 | интерпретатор графа правила: трёхзначная логика, трасса вычисления, вердикт |
| 2 | `backend/app/services/formula_eval.py` | 582 | 13 | вычислитель выражений через разбор в синтаксическое дерево, без обращения к `eval` |
| 3 | `backend/app/services/validator.py` | 530 | 12 | структурная проверка графа правила и критериев решённости |
| 4 | `backend/app/services/regulation_analysis.py` | 471 | 11 | анализ непротиворечивости и пробелов регламента |
| 5 | `backend/app/services/forecast.py` | 200 | 5 | вероятностная оценка доли успеха по правилу Лапласа |
| | **Итого** | **2 824** | **64 + титульный = 65** | |

**Калибр подсчёта листов.** Принято 47 строк на лист — величина взята не из общих соображений, а из образца: в нём 2 205 строк исходного текста дали 47 листов. Окончательное число листов определяется после преобразования в печатный формат и проставляется на титульном листе.

**Почему отобрано именно это.** Депонируемые материалы должны идентифицировать программу, а не показывать её объём. Перечисленные файлы отвечают на вопрос «что это за программа» полнее, чем те же 64 листа, отобранные подряд: первые два задают исполнение регламента и вычисление выражений, следующие два — проверку и анализ, последний — вероятностную оценку. Объектная модель языка (`backend/app/schemas/domain.py`, 757 строк) в отбор не вошла только по объёму: с ней подача выходит за предел в 70 листов. Отраслевые модули, интерфейс и вспомогательные сценарии не входят: первые не принадлежат изделию, вторые и третьи заменимы без изменения существа решения.
