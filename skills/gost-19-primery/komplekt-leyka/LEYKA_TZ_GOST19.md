## 1. Введение

### 1.1 Наименование программы

Полное наименование: **«LEYKA — Система управления проектами центра искусственного интеллекта»** (далее — Система, LEYKA).  
Аббревиатура: **LEYKA** (*Lightweight Engineering Yard for Knowledge Activities*).

### 1.2 Краткая характеристика области применения

Система предназначена для автоматизации управления проектной деятельностью в исследовательских центрах в сфере искусственного интеллекта (ЦИИ), финансируемых Министерством экономического развития Российской Федерации в рамках федерального проекта «Искусственный интеллект» национального проекта «Цифровая экономика».

Основная область применения — Центр искусственного интеллекта Новосибирского государственного университета (ЦИИ НГУ), с возможностью тиражирования на все 13 ЦИИ первой и второй волны отбора.

Система решает задачу автоматизированного сбора, хранения и отображения данных по 11 обязательным показателям результативности (KPI) согласно Приложению №2 к Правилам экспертизы, утверждённым Минэкономразвития России.

### 1.3 Условное обозначение

Шифр разработки: **ЦИИ-НГУ-LEYKA-2026**

## 3. Назначение разработки

### 3.1 Функциональное назначение

LEYKA предназначена для:

1. **Управления проектами** — ведение полного жизненного цикла проекта (пресейл → активный → пауза → завершён → архив) под конкретных заказчиков и грантодателей;
2. **Управления задачами** — канбан-доска с 6 статусами (inbox / todo / in_progress / waiting / review / done), приоритетами P1–P4 и типами (задача / идея / баг);
3. **Учёта KPI Минэкономразвития** — автоматический сбор фактов по 11 метрикам (z-1..z-11) с привязкой к проектным обязательствам, доказательной базой (до 10 свидетельств на факт) и расчётом прогресса;
4. **Управления документооборотом** — чек-лист из ~40 рекомендованных артефактов по 12 стадиям жизненного цикла проекта (переговоры, ТЗ, НИР, ОКР, испытания, сдача, отчётность и др.);
5. **Управления доступом (RBAC)** — двухуровневая система ролей: глобальная должность + проектная роль с 12 флагами прав; 3 режима видимости (private / public / demo);
6. **Отображения витрины достижений** — публичная страница достижений ЦИИ с 7 типами артефактов (статья, ПО, изобретение, датасет, событие, внедрение, прототип);
7. **Аналитики** — показатели скорости закрытия задач (число задач, переведённых в статус «Готово» по неделям) и среднего времени от создания задачи до её завершения; аналитический дашборд KPI для директора центра с цветовой индикацией состояния плана (красный / оранжевый / жёлтый / зелёный / тёмно-зелёный).

### 3.2 Эксплуатационное назначение

Система эксплуатируется ежедневно сотрудниками ЦИИ в режиме веб-приложения через браузер без установки дополнительного ПО. Типовой профиль пользователей: менеджеры проектов, разработчики, аналитики, кураторы (надзорная роль), внешние заказчики и директор центра.

Система работает без VPN, не зависит от зарубежных мессенджеров, данные хранятся на российской инфраструктуре.

## 4. Требования к программе

### 4.1 Требования к функциональным характеристикам

#### 4.1.1 Состав выполняемых функций

**Подсистема аутентификации и авторизации:**
- Вход через OAuth 2.0 (Mail.ru, Google), резервный вход через логин/пароль (root);
- JWT в HttpOnly cookie (SameSite=Lax, Secure на проде), TTL 7 суток;
- CSRF-защита OAuth-флоу через случайный state в short-TTL cookie;
- Цепочка приглашений: управляемый онбординг без самостоятельной регистрации;
- Защита последнего активного администратора от самоудаления/разжалования.

**Подсистема управления партнёрами:**
- CRUD заказчиков/грантодателей с типами (enterprise / government / startup / research);
- Цветовая идентификация в боковой панели (8-цветная палитра + hash-fallback);
- Два режима видимости: private / public;
- Автосоздание пресейл-проекта при создании партнёра.

**Подсистема управления проектами:**
- CRUD проектов с привязкой к партнёру;
- 5 стадий жизненного цикла: presale → active → paused → completed → archived;
- Три режима видимости: private / public / demo;
- Управление бюджетом, сроками, командой;
- Аналитика по проекту: скорость закрытия задач и среднее время выполнения.

**Подсистема управления задачами (Kanban):**
- 6 статусов: inbox / todo / in_progress / waiting / review / done;
- 4 приоритета: P1 (критично) — P4 (низкий);
- 3 типа: задача / идея / баг;
- Drag-and-drop карточек на канбан-доске (dnd-kit);
- Критерий выполнения задачи (обязательная верификация при переводе в done);
- Immutable author_id — автор задачи не изменяется (для статистики);
- История переходов статусов (task_status_history) с аудит-следом.

**Подсистема комментариев и коммуникаций:**
- Лента комментариев внутри задачи с @-упоминаниями;
- Двойные галочки прочтения (comment_read_receipts);
- Автоматическое сворачивание длинных URL в компактные чипы;
- Связывание задач через UUID-ссылки.

**Подсистема документооборота:**
- Чек-лист из ~40 рекомендованных артефактов по 12 стадиям;
- Логика «по умолчанию выключено» — менеджер включает нужные слоты;
- Вложения как URL-ссылки на Яндекс.Диск, Google Docs, GitHub;
- Drag-and-drop файлов во временную папку Google Drive (до 15 МБ, 13 расширений);
- Graceful degradation: если Google Drive не настроен — отдаётся 503, остальное работает.

**Подсистема KPI:**
- Каталог 11 обязательных метрик z-1..z-11 (Приложение №2 Правил экспертизы);
- Годовой план центра по каждой метрике (директор);
- Проектные обязательства по KPI (менеджер) с опциональной квартальной контрольной точкой `target_quarter ∈ {1..4}` и годом `target_year ∈ [2024..2100]`. UNIQUE по `(project, kpi, target_quarter, target_year)` — допускаются многолетние milestone'ы («Q3 2024, Q3 2025, Q3 2026 = 3 разных обязательства»). Backfill: заведение обязательств и фактов задним числом для архивов 2024-25 и витрины прошлых лет;
- Факты достижений (KpiAchievement) с множественными доказательствами (до 10) и датой `occurred_at` (по умолчанию today, можно ставить задним числом для backfill);
- Расчёт прогресса: план / взято проектами / закрыто фактами;
- 4-слойное табло метрик («термометр года»): корона `year_progress` (cumulative-as-of-now) сверху + стопка слоёв Q1..Q4;
- Цветовая палитра: 🔴 <30% / 🟠 30–70% / 🟡 70–100% / 🟢 ≥100% / 🟢🟢 перевыполнение / 🔵 запланирован будущий квартал / ⚪ план не задан.

**Прогноз контрольных точек KPI:**
- Светофор риска срыва (`green / yellow / red`) для каждого квартального обязательства, рассчитывается из плана, накопленных фактов и оставшихся дней до конца квартала;
- Двухуровневый прогноз: центровой (для администратора) + проектный (для менеджера, видит свои риски проактивно);
- Виджет на главной странице «Сообщения» для администратора центра — баннер «N KP под угрозой» с переходом к подробному прогнозу.

**Витрина достижений ЦИИ:**
- Публичная страница с 7 типами артефактов;
- Автоматическое определение типа по domain URL (arxiv.org → статья, patents.google.com → изобретение и др.);
- Выбор «маркетинговой» ссылки из набора доказательств для витрины.

**Управление доступом (RBAC):**
- Уровень 1: должность сотрудника (8 значений, информационный тег);
- Уровень 2: проектная роль (6 ролей, 12 permission-флагов, настраивается администратором);
- is_superuser: обходит все проверки, защищён от само-разжалования;
- Матрица прав редактируется через UI без деплоя.

#### 4.1.2 Организация входных и выходных данных

**Входные данные:**
- Пользовательский ввод через веб-интерфейс (браузер);
- OAuth-токены провайдеров (Mail.ru, Google);
- Файлы документов через drag-and-drop (PDF, DOCX, XLSX, PPTX, PNG, JPG, MD, TXT, CSV; до 15 МБ);
- URL-ссылки на внешние хранилища (Яндекс.Диск, Google Drive, GitHub, arXiv, Роспатент).

**Выходные данные:**
- Канбан-доски с задачами в браузере;
- KPI-дашборды с прогресс-барами и цветовой индикацией;
- Чек-листы документации проектов;
- Витрина достижений ЦИИ;
- REST API (OpenAPI 3.1, Swagger UI) для интеграций;
- Аналитика проекта: скорость закрытия задач и время выполнения (JSON через GET /projects/{id}/analytics).

#### 4.1.3 Временны́е характеристики

| Операция | Целевое время отклика |
|---|---|
| Загрузка SPA (первый визит, CDN) | ≤ 2 сек |
| Загрузка SPA (повторный визит, кэш) | ≤ 0,5 сек |
| Optimistic update задачи в UI | 0 мс (мгновенно) |
| Подтверждение сервера (PATCH задачи) | ≤ 700 мс |
| Получение списка задач проекта | ≤ 500 мс |
| Расчёт KPI-дашборда | ≤ 1 сек |

### 4.2 Требования к надёжности

- Доступность системы: **≥ 99%** в рабочие часы (8:00–22:00 МСК);
- Отказоустойчивость: при недоступности Google Drive API система продолжает работу (graceful degradation — 503 только на upload-endpoint);
- Корректность данных: оптимистичное обновление интерфейса с автоматическим откатом при ошибке сервера;
- Защита от потери данных: SQLite в режиме WAL на постоянном томе Railway (Persistent Volume);
- **Резервное копирование (backup/restore):**
  - Эндпоинт `GET /api/v1/backup/export` — атомарный снимок БД через нативный SQLite backup-API (Connection.backup, не блокирует транзакции). Доступ: администратор центра либо менеджер хотя бы одного проекта.
  - Эндпоинт `POST /api/v1/backup/import` — восстановление БД из ZIP-архива. Доступ: только администратор центра.
  - Формат архива: ZIP с двумя файлами — `leyka.db` (бинарный SQLite-файл) и `manifest.json` (версия формата, версия приложения, дата создания, количество записей по основным таблицам).
  - При восстановлении старая БД сохраняется рядом как `leyka.db.before-restore` (страховка от ошибочного восстановления).
  - Опционально: nightly snapshot через `systemd`-таймер (см. `deploy/nsu-server/leyka-backup.timer`) с retention-политикой 7 дневных + 4 недельных снимков.
- Аудит-след: все переходы статусов задач фиксируются в таблице `task_status_history` (запись о переходе с указанием прежнего и нового статуса, времени и автора);
- Защита последнего администратора: система запрещает удаление, деактивацию и разжалование последнего активного администратора;
- Тестовое покрытие: 345 автоматизированных тестов back-end (pytest), 176 автоматизированных тестов front-end (Vitest), статическая проверка типов TypeScript в строгом режиме (`tsc --noEmit`, 0 ошибок).

### 4.3 Условия эксплуатации

- Система эксплуатируется **круглосуточно** в режиме SaaS;
- Обслуживающий персонал: системный администратор ЦИИ (1 чел.), ответственный за настройку OAuth, Google Drive, переменных окружения;
- Не требует установки на рабочих местах пользователей;
- Работа через браузер: Chrome 120+, Firefox 121+, Safari 17+, Edge 120+;
- Не требует VPN — работает на российских доменах;
- Хранение данных: Railway Persistent Volume (Европа, West), опционально перенос на Yandex Cloud / VK Cloud по требованию заказчика.

#### 6.1.5 Ключевые конкурентные преимущества

1. **Единственная российская система** с встроенными 11 KPI из Правил экспертизы Минэкономразвития — конкурентов с аналогичной специализацией не существует;
2. **Работает без VPN** — критично в условиях 2025–2026 г., когда Telegram требует VPN для государственных учреждений;
3. **Полный стек документооборота по ГОСТ** — чек-листы по 12 стадиям, 40+ каталожных артефактов (НИР, ОКР, ТЗ, ПМИ, акты сдачи);
4. **Открытый исходный код** — снижает барьер доверия, каждый центр может развернуть собственный экземпляр;
5. **Малый TCO** — хостинг ~20 000 ₽/мес против 90 000–1 200 000 ₽/мес у коммерческих аналогов на 200 пользователей.

### 6.2 Ориентировочная потребность

Система ориентирована на:
- **Первичный рынок:** 13 Центров ИИ Минэкономразвития России (~200–300 сотрудников каждый);
- **Вторичный рынок:** НИИ, вузовские лаборатории, технологические партнёры центров;
- **Стратегический рынок:** потенциальное включение LEYKA в единую цифровую платформу Минэкономразвития для учёта результатов R&D-центров.

## 8. Порядок контроля и приёмки

### 8.1 Виды испытаний

| Вид испытаний | Методика | Ответственный |
|---|---|---|
| Автоматизированное тестирование back-end | pytest + httpx + SQLite in-memory, 288 тестов | Разработчик |
| Автоматизированное тестирование front-end | Vitest, 176 тестов (lib/, store/, components/About) | Разработчик |
| Статическая проверка типов front-end | `tsc -b --noEmit` (TypeScript strict) | Разработчик |

| Нагрузочное тестирование | locust (планируется при росте до >100 одновременных пользователей) | DevOps |
| Приёмочные испытания | Демонстрация директору ЦИИ НГУ и представителю Минэкономразвития | Заказчик |

### 8.2 Общие требования к приёмке

Программа считается принятой при одновременном выполнении следующих условий:

1. Все 288 автотестов back-end проходят без ошибок (`pytest -v`: 288 passed, 0 failed, 0 errors);
2. Все 176 автотестов front-end проходят без ошибок (`npx vitest run`: 176 passed, 0 failed);
3. Статическая проверка типов front-end проходит без ошибок (`npx tsc -b --noEmit`: 0 errors);
4. Производственная сборка front-end собирается без ошибок (`npm run build`);
5. Вход через OAuth Mail.ru и/или Google работает на промышленном экземпляре;
6. Дашборд KPI центра отображает данные по всем 11 метрикам (z-1 … z-11);
7. Канбан-доска отображает задачи и допускает перенос карточек методом drag-and-drop;
8. Чек-лист документации проекта отображает все 12 стадий и позволяет прикреплять ссылки и загружать файлы во временную папку;
9. Время отклика API ≤ 700 мс на 95-м перцентиле при нормальной нагрузке (≤ 50 одновременных пользователей).

### 8.3 Средства тестирования

- **Back-end:** `pytest` 9.0, `pytest-asyncio` 1.3, `httpx.AsyncClient`, `aiosqlite` (in-memory, StaticPool);
- **Front-end:** `vitest` 2.1 (Node-environment, без jsdom — для pure-функций и stores);
- **Типизация:** `tsc --noEmit` (TypeScript 5.6, strict);
- **API-тестирование (ручное):** Swagger UI на промышленном экземпляре — `https://leyka-production.up.railway.app/docs`;
- **CI:** автоматический запуск Vercel- и Railway-сборок при push в `main`; GitHub Actions — планируется в Phase 8.
