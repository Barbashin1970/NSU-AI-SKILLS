### 2.3 База данных

**СУБД:** SQLite в режиме WAL (Write-Ahead Logging) на постоянном томе. Единый режим для dev и prod. Объём БД на горизонте 5 лет — оценочно <100 МБ. Миграция на PostgreSQL не планируется (обоснование — `SKILL-INFRA.md`).

**Файл БД (по умолчанию):**

| Среда | Путь к файлу |
|---|---|
| Локальная разработка | `./backend/leyka.db` |
| Railway (облако) | `/data/leyka.db` (на персистентном томе) |
| Сервер ЦИИ НГУ | `/var/lib/leyka/leyka.db` |

Сопутствующие файлы (создаются SQLite автоматически):
- `<имя>.db-wal` — журнал WAL (накопленные изменения, ещё не записанные в основной файл);
- `<имя>.db-shm` — shared memory (блокировки и индексы WAL).

Файлы-страховки (создаются программой при операциях восстановления):
- `<имя>.db.before-restore` — копия БД, существовавшая до операции восстановления (см. §9.3);
- `<имя>.db.failed` — копия БД, существовавшая до операции отката (создаётся `POST /backup/rollback` или CLI-скриптом).

## 4. Настройка программы

### 4.1 Переменные окружения

Все настройки задаются через переменные окружения (на Railway — Variables, на сервере НГУ — `/etc/leyka/.env`). Полный список — в Приложении А. Здесь — критичные.

| Переменная | Обязательно? | Назначение |
|---|---|---|
| `DATABASE_URL` | да | Путь к SQLite-файлу. Пример: `sqlite+aiosqlite:////data/leyka.db` (4 слэша = абсолютный путь) |
| `JWT_SECRET` | да в проде | Секрет для подписи JWT-токенов. ≥32 символа. Сгенерировать: `openssl rand -hex 32` |
| `IS_PRODUCTION` | да в проде | `true` — включает startup fail-fast (см. §13.1) |
| `AUTH_COOKIE_SECURE` | да в проде | `true` — cookie только по HTTPS |
| `ENABLE_MOCK_AUTH` | да в проде | `false` — отключает фейковый mock-логин |
| `ROOT_EMAIL` | да | E-mail первого администратора (создаётся сидером) |
| `ROOT_PASSWORD` | временно | Установка пароля root через `set_root_password.py`. Удалить после применения |
| `MAILRU_CLIENT_ID`, `MAILRU_CLIENT_SECRET`, `MAILRU_REDIRECT_URI` | для Mail.ru | OAuth-приложение в кабинете Mail.ru |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` | для Google | OAuth-приложение в Google Cloud Console |
| `GDRIVE_REFRESH_TOKEN`, `GDRIVE_FOLDER_ID` | для Drive | Загрузка файлов в Google Drive (см. §4.3) |
| `BACKUP_ROLLBACK_TOKEN` | временно (аварийно) | Включает аварийный rollback-эндпоинт (см. §9.3). По умолчанию пусто — эндпоинт выключен |
| `CORS_ORIGINS` | да | Список доменов фронтенда (например, `["https://leyka-nsu.vercel.app"]`) |
| `AUTH_SUCCESS_REDIRECT` | да | URL фронтенда, куда возвращается юзер после OAuth |

### 4.2 Аутентификация и провайдеры OAuth

Поддерживаются провайдеры:
- **Mail.ru** — основной для сотрудников НГУ (Mail.ru-почта распространена);
- **Google** — для тех, у кого корпоративный Google-аккаунт;
- **Yandex** — резервный (поддержка из коробки, требует регистрации приложения);
- **VK** — резервный;
- **Local** (e-mail + пароль) — единственный путь для root-администратора при недоступности OAuth-провайдеров.

Регистрация приложений в кабинетах провайдеров — см. ИУ.001 §4.1, §4.2.

**Важно:** при логине auth-сервис ищет пользователя по `email == X OR alternative_email == X`. Это позволяет одному человеку иметь склеенные учётки Gmail+Mail.ru (см. §5.4 — слияние учёток).

### 4.3 Хранилище файлов (Google Drive)

LEYKA не хранит файлы в собственной БД — только URL. Загрузка файлов через drag-and-drop работает через Google Drive API: файл уходит в личный Drive администратора (через refresh_token), ссылка попадает в задачу или чек-лист.

**Настройка:** разовая, выполняется через `python -m scripts.authorize_gdrive`. Получает `refresh_token` через OAuth user-flow. Записывается в env как `GDRIVE_REFRESH_TOKEN`.

Подробности — в ИУ.001 §4.4 и `GOOGLE_DRIVE_SETUP.md` (если файл присутствует в репозитории).

**Что делать если Drive отвалится:** `POST /api/v1/uploads/*` отвечает 503. Это graceful degradation — система продолжает работать, drag-and-drop временно недоступен (юзеры вручную копируют ссылки в задачи). Восстановить `GDRIVE_REFRESH_TOKEN` через `authorize_gdrive`.

## 5. Управление учётными записями

### 5.1 Создание первого администратора

При первичной установке скрипт `scripts/seed.py` (запускается автоматически в составе `setup.sh` или при первом старте через `alembic upgrade head`) создаёт первого администратора с e-mail из `ROOT_EMAIL`. Пароль не выставляется — вход возможен только через OAuth с тем же e-mail.

Чтобы установить пароль (для local-логина):

```bash
# 1. В .env добавить временно:
ROOT_PASSWORD=<временный_пароль>

# 2. Применить:
cd /opt/leyka  # или путь к проекту
sudo -u leyka /opt/leyka/.venv/bin/python -m scripts.set_root_password

# 3. Удалить ROOT_PASSWORD из .env (защита от повторного использования)
```

Скрипт идемпотентен: повторный запуск с тем же паролем — no-op.

### 5.2 Повышение пользователя до администратора

```bash
# Сделать пользователя <email> администратором:
sudo -u leyka /opt/leyka/.venv/bin/python -m scripts.promote_admin <email>
```

Альтернативно — через UI: войти как существующий admin → меню профиля → «Пользователи центра» → найти юзера → редактировать → поставить галку «Администратор» → сохранить.

### 5.3 Установка/сброс пароля root-учётной записи

См. §5.1. Скрипт `scripts.set_root_password` работает только с e-mail из `ROOT_EMAIL`. Для смены пароля другому юзеру — через UI редактирования профиля либо через `scripts.promote_admin` (если требуется заодно повысить до admin).

### 5.4 Слияние двух OAuth-учёток одного человека

Типичная ситуация: сотрудник вошёл в систему через Gmail (создалась учётка `ivanov@gmail.com`), потом залогинился через Mail.ru (создалась вторая учётка `ivanov@mail.ru`). В системе два разных профиля одного человека — задачи, комментарии и проекты разделены.

**Решение через UI:**

1. Меню профиля → «Пользователи центра» → найти первую учётку → нажать иконку **«Combine»** (слияние).
2. В открывшейся модалке через поиск найти вторую учётку → выбрать → нажать **«Слить»**.
3. Подтвердить операцию в native-confirm с предупреждением.
4. После слияния:
   - все задачи, комментарии, лайки, материалы вики и членство в проектах второй учётки переходят к первой;
   - e-mail второй учётки сохраняется как `alternative_email` у первой — пользователь может логиниться по любому из двух адресов в один и тот же аккаунт;
   - при конфликте ролей в проекте остаётся роль с бо́льшими правами;
   - вторая учётка удаляется.

**Защиты:**
- Только администратор может выполнить слияние.
- Запрещено сливать единственного активного администратора в обычного юзера (lockout-защита).
- Все факты слияния пишутся в журнал сервера с пометкой `WARNING leyka.users: users merge by admin=…`.

**Ручная установка `alternative_email`** (без слияния): через UI редактирования профиля → поле «Альтернативный e-mail» → сохранить. Полезно, если у пользователя есть третья почта и нужно дать вход по ней без удаления учёток (но при этом задачи и комментарии не переносятся — только разрешается логиниться по дополнительному адресу).

### 5.5 Деактивация и удаление пользователей

| Операция | Когда применять | Доступ |
|---|---|---|
| **Деактивация** (`is_active=false`) | Сотрудник ушёл из ЦИИ — данные нужно сохранить, но логин запретить | Администратор |
| **Удаление** (`DELETE /users/{id}`) | Тестовая учётка, дубль до настройки слияния, ошибочная регистрация | Администратор |

Деактивация — soft-delete: учётка остаётся в БД, задачи и комментарии не теряют автора, но юзер не может зайти. Включить обратно — снять галку «Активен» в редактировании профиля.

Удаление — hard-delete: учётка стирается. Связанные данные обрабатываются:
- `ProjectMember` — каскадно удаляются;
- `assignee_id` у задач, `author_id` у комментариев, `created_by_id` у вложений и KPI-фактов — обнуляются (история проекта сохраняется, в UI отображается «—»);
- `comment_read_receipts` — каскадно удаляются.

### 5.6 Защита от потери последнего администратора

Система запрещает следующие операции, если они оставят систему без активных администраторов:
- Снять флаг `is_superuser` у самого себя (через PATCH профиля);
- Деактивировать самого себя (`is_active=false`);
- Удалить себя (DELETE);
- Слить себя в обычного юзера через merge (`POST /users/{id}/merge`).

В этих случаях возвращается HTTP 400 с сообщением «Нельзя оставить систему без администратора». Чтобы провести такую операцию — сначала повысить другого активного юзера до admin, потом операцию повторить.

## 6. Управление ролями и матрицей прав

В системе шесть проектных ролей с дискретными правами (12 permission-флагов). Полная матрица — в Приложении А руководства пользователя (РП.001). Управление — через UI: меню профиля → «Управление доступом».

| Роль | Когда назначать |
|---|---|
| **Менеджер** | Руководитель проекта — все права в проекте, включая публикацию в WIKI |
| **Разработчик** | Исполнитель — может вести и комментировать задачи, не управляет бюджетом и составом |
| **Аналитик** | Документация — может писать ТЗ, протоколы; роль аналогична разработчику |
| **Наблюдатель** | Внешний заказчик/куратор — только читает и комментирует |
| **Куратор** | Надзорная роль — видит бюджет и конфиденциальную wiki, не правит |
| **Заказчик** | Клиент проекта — видит ход работ и комментирует |

**Правка флагов:** администратор может изменить набор прав любой роли (например, разрешить «Аналитику» публиковать в WIKI). Изменение применяется ко всем участникам с этой ролью одновременно.

**Право `can_edit_wiki`:** изначально (после миграции на новую модель библиотеки знаний 26 апреля 2026) даётся только Менеджеру. Это сделано умышленно — защита от случайного засорения общей библиотеки центра. Если требуется разрешить аналитикам/разработчикам публиковать — администратор включает флаг через UI.

## 7. Управление проектами и заказчиками

Администратор не обязан управлять проектами и заказчиками — это работа менеджеров. Однако администратор имеет:
- **Полную видимость** всех проектов центра (даже частных, в которых не состоит участником);
- **Возможность переноса проекта между заказчиками** (через PATCH `/projects/{id}` с новым `partner_id`);
- **Возможность принудительной смены менеджера** (если основной менеджер недоступен) через изменение `ProjectMember.role_id`.

В обычной работе администратор подключается только при инцидентах: сотрудник уволился без передачи проекта, заказчик переименован, проект нужно архивировать.

## 9. Резервное копирование и восстановление

### 9.1 Скачивание резервной копии

**Кому доступно:** администратор + менеджер любого проекта (как страховка). Менеджеры качают копию для своего архива; восстановить из неё может только администратор.

**Как:** меню профиля → «Резервная копия» → «Скачать сейчас». Браузер сохранит файл `leyka-backup-YYYY-MM-DD-HHMM.zip`.

**Что внутри ZIP:**
- `leyka.db` — атомарный снимок SQLite через нативный backup-API (не блокирует живые транзакции);
- `manifest.json` — формат, версия приложения, дата (UTC), число записей по таблицам (для сверки).

**Регламент:** см. §15 — администратор обязан скачивать резервную копию **минимум раз в неделю**, дополнительно — перед каждым обновлением системы.

### 9.2 Восстановление из резервной копии

**Доступ:** только администратор.

1. Меню профиля → «Резервная копия» → секция «Восстановить из файла».
2. Нажать «Выбрать ZIP-файл» → указать ранее сохранённый архив.
3. Нажать «Восстановить» → подтвердить в native-confirm.
4. Получить уведомление об успехе с новым manifest.
5. **Перезапустить серверный сервис** (на Railway — кнопка Restart; на сервере НГУ — `sudo systemctl restart leyka-api`).

Без перезапуска возможны временные сбои: SQLAlchemy кэширует connection pool, и live-запросы могут попасть в момент замены файла.

### 9.3 Аварийный откат (rollback)

Используется в двух случаях:
1. **Восстановили не тот архив** — данные стали некорректными;
2. **Восстановили из старой версии, в которой нет учётной записи администратора** — администратор не может зайти и выполнить штатный restore.

Поскольку штатный restore требует UI-логина, для второго случая предусмотрен аварийный endpoint `POST /api/v1/backup/rollback`, работающий **БЕЗ авторизации** и защищённый секретным токеном из переменной окружения `BACKUP_ROLLBACK_TOKEN`.

**Процедура (рекомендуемая, через Swagger UI):**

1. Открыть панель управления хостингом → Variables / .env:
   - **Railway:** Project → Settings → Variables;
   - **Сервер ЦИИ НГУ:** `sudo nano /etc/leyka/.env`.
2. Добавить переменную с длинной случайной строкой:
   ```
   BACKUP_ROLLBACK_TOKEN=<openssl rand -hex 32>
   ```
3. Дождаться redeploy (~30 сек на Railway, либо `sudo systemctl restart leyka-api` на сервере НГУ).
4. Открыть Swagger UI бэкенда:
   - **Railway:** `https://leyka-production.up.railway.app/docs`;
   - **Сервер НГУ:** `https://<домен-сервера>/docs`.
5. Раздел **Backup** → **POST `/backup/rollback`** → «Try it out» → ввести токен → **Execute**.
6. Получить ответ `{"rolled_back": true, ...}`.
7. Перезапустить сервис.
8. **УДАЛИТЬ `BACKUP_ROLLBACK_TOKEN`** из переменных (защита от повторного использования).

**Альтернатива (CLI):** если есть shell-доступ к серверу, можно использовать `python -m scripts.restore_rollback` (см. Приложение Б). Не требует токена — работает с локального диска напрямую.

**Что произойдёт:**
- Текущий `leyka.db` сохранится как `leyka.db.failed` (на случай, если в нём есть ценное);
- `leyka.db.before-restore` (созданный при предыдущей операции восстановления) станет основным `leyka.db`;
- WAL/SHM-хвосты от плохой БД будут удалены.

**Ограничение:** rollback возможен только **сразу после операции восстановления**. Файл `leyka.db.before-restore` хранится только до следующего restore — потом перезаписывается. Для исторических снимков используется отдельный systemd-таймер (см. §9.4).

### 9.4 Автоматический планировщик снимков (на сервере НГУ)

На сервере НГУ скрипт установки активирует systemd-таймер `leyka-backup.timer`:

```bash
# Проверить статус
sudo systemctl status leyka-backup.timer
# Когда следующий запуск
sudo systemctl list-timers leyka-backup
```

**Что делает:**
- Каждые 6 часов вызывает `sqlite3 leyka.db ".backup …"` (атомарный snapshot, безопаснее `cp`) с последующим сжатием gzip;
- Хранит локально 7 ежедневных + 4 еженедельных копий (rolling);
- В 03:00 ежесуточно — загружает свежий snapshot в удалённое хранилище через `rclone` (Я.Диск, S3-совместимое, NAS).

**Настройка удалённого хранилища** (разово после установки):

```bash
sudo -u root rclone config
# Выбрать тип: yandex / s3 / sftp / ...
# Пройти OAuth-флоу провайдера, назвать remote (например 'yadisk')
```

На Railway собственного аналога нет — используется только встроенный механизм `POST /backup/export` плюс ручное скачивание администратором по регламенту (см. §15).

### 9.5 Стратегия хранения копий

| Уровень | Где | Сколько | Кто следит |
|---|---|---|---|
| Live-БД | `leyka.db` на постоянном томе | 1 актуальная | Сервис автоматически (WAL) |
| Файл-страховка от restore | `leyka.db.before-restore` | 1 последняя | Создаётся автоматически при операции восстановления |
| Файл-страховка от rollback | `leyka.db.failed` | 1 последняя | Создаётся автоматически при rollback |
| Локальные снимки | `/var/lib/leyka/backups/` (только сервер НГУ) | 7 дневных + 4 недельных | systemd-таймер |
| Удалённые снимки | Я.Диск / S3 / NAS (только сервер НГУ) | Ежедневные | rclone в systemd-таймере |
| Ручные копии администратора | Локальный диск админа, корпоративное хранилище | На усмотрение | Регламент §15 |

## 10. Перенос данных между средами

### 10.1 Сценарий: Railway → сервер НГУ

Подробная пошаговая процедура — в `LEYKA_InstallManual_GOST19.md` §6.7. Краткая версия:

1. На Railway скачать backup через UI.
2. Развернуть LEYKA на сервере НГУ (см. ИУ.001 §6).
3. Установить пароль root-админу через `set_root_password.py` (временный).
4. Войти под root → восстановить из ZIP через UI.
5. Перезапустить сервис.
6. Удалить временный `ROOT_PASSWORD` из `.env`.

**Что не переносится:** HttpOnly-cookies сессий (привязаны к старому `JWT_SECRET`) — пользователи проходят аутентификацию заново. Это штатное поведение.

### 10.2 Сценарий: dev → prod

Используется редко (обычно prod-данные идут в dev, а не наоборот — для тестирования). Если нужно:

1. Скачать backup в dev через UI или curl (`curl https://localhost:8000/api/v1/backup/export -o dev-backup.zip` — после логина).
2. Открыть prod как admin.
3. Восстановить через UI.

⚠️ **Опасно:** этот сценарий перетирает реальные данные пользователей в проде. Используйте только для первичной заливки или в экстренных случаях.

### 10.3 Что НЕ переносится автоматически

| Что | Почему | Как переносить |
|---|---|---|
| `JWT_SECRET` | Безопасность: при переезде нужен новый | Сгенерировать заново на новой среде |
| `MAILRU_REDIRECT_URI` / `GOOGLE_REDIRECT_URI` | Привязаны к домену | Обновить в OAuth-кабинетах провайдеров |
| `GDRIVE_REFRESH_TOKEN` | Привязан к Google-аккаунту, который проходил `authorize_gdrive` | Запустить `authorize_gdrive` на новой среде |
| Файлы в Google Drive | Хранятся вне LEYKA | Drive продолжает работать сам — LEYKA хранит только URL |
| Сессии пользователей | HttpOnly-cookies подписаны старым `JWT_SECRET` | Пользователи логинятся заново |

## 11. Обновление программы (релизы)

### 11.1 Деплой на Railway (автоматический через git push)

Railway настроен на автоматический деплой при push в ветку `main`. Процедура релиза:

1. Разработчик мерджит PR в `main` через GitHub.
2. Railway видит новый коммит → начинает сборку (~1–2 минуты).
3. После сборки выполняется `start.sh`: `alembic upgrade head` + `uvicorn …`.
4. Если миграции прошли и сервис ответил health-check — Railway перенаправляет трафик на новый деплой.
5. Старый деплой остаётся доступен ~5 минут на случай отката.

**Действия администратора:** перед мерджом крупных изменений — скачать backup БД (см. §9.1) на свой диск, **дополнительно к автоматическим**.

### 11.2 Деплой на сервер НГУ (вручную)

```bash
cd /opt/leyka
sudo git pull
# Пересобрать фронтенд (если был изменён frontend/)
sudo -u leyka bash -c "cd frontend && npm ci && npm run build"
# Применить миграции БД (если были)
sudo -u leyka /opt/leyka/.venv/bin/python -m alembic upgrade head
# Перезапустить сервис
sudo systemctl restart leyka-api
# Проверить
curl https://<домен-сервера>/health
```

**Перед обновлением — обязательно бэкап** (см. §9.1) и сохранить локальную копию.

### 11.3 Применение миграций БД

Миграции (Alembic) применяются автоматически при старте сервиса. Файлы — в `backend/migrations/versions/`.

**Откатить миграцию вручную:**

```bash
# Посмотреть текущую версию
sudo -u leyka /opt/leyka/.venv/bin/python -m alembic current

# Откатить на 1 версию назад
sudo -u leyka /opt/leyka/.venv/bin/python -m alembic downgrade -1

# Откатить до конкретной версии
sudo -u leyka /opt/leyka/.venv/bin/python -m alembic downgrade 0024_kpi_evidences
```

⚠️ **Важно:** не каждая миграция корректно откатывается (некоторые `downgrade()` не поддерживают потерю данных). Перед откатом — сделать backup (см. §9.1).

### 11.4 Откат релиза

**На Railway:** Dashboard → Deployments → выбрать предыдущий успешный → «Redeploy». Откатывает только код. Если новый код добавил миграции, и они применились к БД — нужен дополнительно откат миграции (§11.3).

**На сервере НГУ:**

```bash
cd /opt/leyka
sudo git log --oneline -10  # увидеть коммиты
sudo git reset --hard <hash_предыдущего_рабочего_коммита>
# Если миграции были — откатить их (см. §11.3)
sudo -u leyka /opt/leyka/.venv/bin/python -m alembic downgrade <previous>
# Перезапустить
sudo systemctl restart leyka-api
```

## 12. Мониторинг и диагностика

### 12.1 Health-endpoint и проверки

В системе два уровня health-проверок:

**`GET /health`** — минимальная (liveness probe для хостинга):

```bash
curl http://127.0.0.1:8000/health
# {"status":"ok","service":"leyka-api","version":"0.2.0"}
```

Используется Railway / nginx / UptimeRobot для проверки «живой ли процесс». Не требует доступа к БД — отвечает мгновенно.

**`GET /api/v1/health/deep`** — расширенная диагностика:

```bash
curl https://<домен>/api/v1/health/deep
# {
#   "status": "ok" | "degraded" | "down",
#   "traffic_light": "green" | "yellow" | "red",
#   "checks": {
#     "database": "ok",
#     "active_admin_count": 2,
#     ...
#   },
#   "errors_last_24h": 0,
#   "recent_errors": [...],
#   "checked_at": "2026-04-27T12:34:56+00:00"
# }
```

Делает реальный SELECT в БД (через `count(*) FROM users WHERE is_superuser`), отдаёт сводку по последним ошибкам и цвет светофора:

| traffic_light | Условие | Что значит для админа |
|---|---|---|
| 🟢 `green` | За 24 часа ошибок БД нет | Всё штатно, никаких действий не требуется |
| 🟡 `yellow` | Были ошибки за сутки, но сейчас система отвечает | Заглянуть в логи, понять причину; обычно временный сбой OAuth-провайдера или сетевой glitch |
| 🔴 `red` | ≥3 ошибки БД за последние 5 минут или DB-read провалился | Срочное вмешательство: проверить место на диске, статус процесса, целостность БД |

**Светофор в UI:** в шапке профиля администратора (рядом с чипом имени, видно только администратору) встроена цветная иконка базы данных, polling этого endpoint каждые 30 секунд. Клик по иконке открывает popover с деталями: счётчик за 24 часа, последние 5 ошибок с request_id (для поиска в логах) и timestamp последней проверки.

**Подключение к мониторингу:** UptimeRobot / Healthchecks.io можно навесить на `/api/v1/health/deep` с алертом при `status != "ok"`. Endpoint публичный (без auth) — UI должен работать в т.ч. на login-экране, и uptime-monitor дёргает без cookie. Из endpoint'а **не утекают** имена/email/тексты задач — только агрегированная сводка и request_id'ы.

### 12.2 Чтение логов сервера

**На сервере НГУ:**

```bash
# Логи в реальном времени
sudo journalctl -u leyka-api.service -f

# Последние 200 строк
sudo journalctl -u leyka-api.service -n 200

# Логи за сегодня
sudo journalctl -u leyka-api.service --since today
```

**На Railway:** Dashboard → Service → Logs (real-time stream).

### 12.3 Идентификатор запроса (request_id) и разбор инцидентов

При любой ошибке (5xx, 4xx) в ответе сервера присутствует поле `request_id` (короткий hex-id, 12 символов). Также этот id попадает в HTTP-заголовок `X-Request-Id` и в серверный лог.

**Что делать при жалобе пользователя:**
1. Попросить пользователя прислать `request_id` из сообщения об ошибке.
2. Найти в логах: `sudo journalctl -u leyka-api.service | grep <request_id>` (или поиск в Railway Logs UI).
3. Увидеть полную трассировку с traceback.
4. Если это баг — завести issue в репозитории с приложенным traceback.

### 12.4 Swagger UI для прямой работы с API

Swagger UI доступен по `/docs` на любом инстансе бэкенда:

- **Railway:** `https://leyka-production.up.railway.app/docs`;
- **Сервер НГУ:** `https://<домен-сервера>/docs`;
- **Локально:** `http://localhost:8000/docs`.

Используется администратором для:
- Прямого вызова эндпоинтов (с авторизацией через cookie или без — для специальных эндпоинтов вроде `/backup/rollback`);
- Проверки контракта (схемы запросов и ответов);
- Изучения, какие эндпоинты в системе вообще есть (87 на момент написания).

## 13. Безопасность

### 13.1 Контроль обязательных переменных в проде

Программа имеет **fail-fast при старте в проде** (см. `app/main.py:_enforce_production_safety()`). Если `IS_PRODUCTION=true`, сервис не поднимется, если:
- `JWT_SECRET` слабый (короче 32 символов или содержит `change-me`, `dev`, `test` и т.п.);
- `ENABLE_MOCK_AUTH=true` (mock-логин даёт вход без проверки пароля);
- `AUTH_COOKIE_SECURE=false` (cookies могут уйти plain-HTTP).

При попытке запуска с такими настройками сервис падает с явным сообщением. Это умышленно — защита от случайной выкатки уязвимой конфигурации.

**Действие администратора:** перед каждым крупным изменением `.env` — проверить, что все три флага соответствуют проду.

### 13.2 Проверка JWT_SECRET и cookie

`JWT_SECRET` — ключ подписи всех JWT-токенов. Если он утекает — атакующий может выпустить токен под чужой `user_id`.

Регламентная проверка:
- Раз в год — ротация `JWT_SECRET`. После замены все активные сессии инвалидируются (юзеры логинятся заново).
- Никогда не коммитить `JWT_SECRET` в git. Только через Railway Variables или `/etc/leyka/.env`.

### 13.3 Аудит-журнал критичных операций

В журнал сервера пишутся (с уровнем `WARNING`):
- Слияние двух учёток (`users merge by admin=…`);
- Восстановление БД (`backup import by user=…`);
- Откат БД (`backup rollback: SUCCESS`);
- Все ошибки с `request_id`.

При расследовании инцидента (например, «куда делась учётка Иванова?») — проверить журнал по слову `merge` за нужный период.

### 13.4 Удаление временных секретов после использования

Список переменных, которые ставятся **временно** для разовых операций и удаляются после:

| Переменная | Когда ставится | Когда удалять |
|---|---|---|
| `ROOT_PASSWORD` | Для применения через `set_root_password.py` | Сразу после успешного применения |
| `BACKUP_ROLLBACK_TOKEN` | Для аварийного rollback | Сразу после успешного отката |

⚠️ Оставленный `BACKUP_ROLLBACK_TOKEN` = открытый канал переустановки БД для всех, кто узнает токен. Удалять обязательно.

### 13.5 Отзыв OAuth-секретов

Если есть подозрение на компрометацию OAuth-приложения (Mail.ru / Google):

1. Зайти в кабинет провайдера → найти приложение «LEYKA» → перевыпустить `client_secret`.
2. Обновить переменную `<PROVIDER>_CLIENT_SECRET` в Railway / `/etc/leyka/.env`.
3. Дождаться redeploy / перезапустить сервис.
4. Действующие сессии пользователей продолжают работать (они подписаны `JWT_SECRET`, не OAuth-токеном).

### 14.1 Сообщения об ошибках на старте сервиса

| Сообщение | Причина | Действие |
|---|---|---|
| `RuntimeError: Небезопасная конфигурация для IS_PRODUCTION=true: …` | Слабый JWT_SECRET, mock-auth включён, cookie не secure | Поправить переменные окружения и перезапустить |

### 14.2 Сообщения в логах при работе

| Сообщение | Причина | Действие |
|---|---|---|
| `WARNING leyka.users: users merge by admin=…` | Прошло слияние двух учёток | Информационное; для аудита |
| `WARNING leyka.backup: backup import by user=…` | Прошло восстановление БД | Информационное; убедиться, что это не сюрприз |

| `ERROR …` с `request_id=…` | Необработанное исключение | Найти полную трассу по `request_id`, завести issue |

## 15. Регламент работы администратора

### 15.1 Ежедневно

| Задача | Время | Что проверять |
|---|---|---|
| Проверка health-endpoint | 5 мин | `curl https://<домен>/health` — должно быть 200 OK |
| Просмотр логов на ошибки | 5 мин | `journalctl -u leyka-api --since today | grep ERROR` |
| Проверка статуса бэкап-таймера (только сервер НГУ) | 2 мин | `systemctl status leyka-backup.timer` |

### 15.2 Еженедельно

| Задача | Время | Действие |
|---|---|---|
| Скачать резервную копию вручную | 5 мин | Меню профиля → «Резервная копия» → «Скачать сейчас». Сохранить в корпоративное хранилище |
| Проверить, что автоматические снимки идут (сервер НГУ) | 5 мин | `ls -la /var/lib/leyka/backups/` — должны быть свежие файлы |
| Проверить дисковое пространство | 5 мин | `df -h` — на разделе с `/var/lib/leyka/` или `/data/` должно быть >50% свободно |
| Проверить статусы новых сотрудников | 10 мин | Меню → «Пользователи центра» — нет ли подозрительных новых учёток (потенциальный leak invite-ссылки) |

### 15.3 Ежемесячно

| Задача | Время | Действие |
|---|---|---|
| Тестовое восстановление | 30 мин | Развернуть LEYKA в тестовой среде, восстановить последний бэкап, убедиться, что данные читаются |
| Архивирование старых проектов | 15 мин | Совместно с менеджерами — перевести закрытые проекты в стадию `archived` |
| Сверка KPI центра | 10 мин | Открыть «KPI центра» — убедиться, что все факты обработаны менеджерами |
| Проверка обновлений зависимостей | 30 мин | Сверить с CVE-базой (security audit) ключевые библиотеки. Применить минорные апдейты |
| Удалить дубликаты учёток | 15 мин | Меню → «Пользователи» → искать пары `user@gmail.com` + `user@mail.ru` → слить через Combine |

### 15.4 По событию (инциденты)

| Событие | Реакция |
|---|---|
| Пользователь сообщает «не могу войти» | Найти учётку в админке, проверить `is_active`. Если нужно — сбросить пароль, проверить альтернативный e-mail, при необходимости слить дубликат |
| Восстановили БД, и админ потерял доступ | Использовать аварийный rollback (§9.3) |
| Ошибка 500 у пользователя | Найти `request_id` в его сообщении, найти в логах traceback, завести issue |
| Подозрение на утечку секретов | Перевыпустить `JWT_SECRET` и/или OAuth-секреты, инвалидировать сессии |
| Падение Railway / недоступность сервера | Проверить статус провайдера, дождаться восстановления, при необходимости — переезд по сценарию §10.1 |
| Превышение лимита диска на томе | Удалить старые снимки из `backups/`, заархивировать на удалённое хранилище, расширить том на хостинге |

### Приложение Б. Сводка скриптов командной строки

Все скрипты запускаются из каталога `backend` от имени системного пользователя сервиса:

| Скрипт | Назначение | Когда применять |

### Приложение Д. Инфраструктурные требования (краткая сводка)

Полный анализ — в репозитории, файл `SKILL-INFRA.md`. Здесь — выжимка для разговора с ИТ-службой НГУ.

**Минимальные ресурсы для запуска LEYKA сбоку от других сервисов:**

| Ресурс | Минимум | Рекомендуется |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| RAM | 256 МБ | 512 МБ |
| Диск | 2 ГБ | 5 ГБ (с запасом на 5 лет данных и rolling-бэкапы) |
| TCP-порт | 1 (например, 8000 для uvicorn) | 1 |
| Public IP | опционально (можно через Cloudflare Tunnel) | опционально |
| Исходящий HTTPS | обязательно | обязательно |

**Системный стек, который должен быть установлен:**

- Python 3.12+ (с пакетами `python3-venv`, `python3-dev`);
- Node.js 20+ и npm — только на момент сборки фронтенда;
- nginx 1.20+ (reverse-proxy + раздача статики + SSL);
- sqlite3 3.40+ с поддержкой FTS5;
- rclone 1.60+ (для удалённых бэкапов);
- git (для обновлений);
- certbot (если есть публичный IP и используется Let's Encrypt).

Установка одной командой на Ubuntu 22.04+:

```bash
sudo apt install -y python3.12 python3.12-venv python3-dev \
                    nodejs npm git nginx sqlite3 rclone certbot
```

Полный список Python-зависимостей — `backend/requirements.txt` (FastAPI 0.115, SQLAlchemy 2.0, aiosqlite, Alembic, Pydantic v2, python-jose, passlib[bcrypt], httpx, google-api-python-client). После сборки фронтенда (`npm run build`) Node.js на production runtime НЕ нужен.

**Docker:** не обязателен. Рекомендуется деплой через systemd-сервис — меньше абстракций, чем у Docker, и админу НГУ привычнее. Bootstrap-скрипт `deploy/nsu-server/setup.sh` использует `python -m venv` для изоляции зависимостей. Docker имеет смысл, только если у НГУ уже есть единый docker-pipeline или нужны параллельные dev/staging-инстансы на одном железе.

**Что ИСКЛЮЧЕНО из вариантов размещения:**

| Вариант | Почему нельзя |
|---|---|
| Ноутбук Windows + UPS «до конца года» | Windows Update раз в неделю → принудительная перезагрузка; крышка/sleep — точка отказа; HTTPS-cert без публичного IP сложно; антивирус НГУ может блокировать listening port |
| Raspberry Pi (любой модели) | SD-карты горят за 6–12 месяцев под write-нагрузкой; не серьёзный формат для корпоративного сервиса |
| Виртуалка на ноутбуке разработчика | То же что Windows-ноутбук + риск, что разработчик сменит машину |
| Бесплатный VPS у иностранного провайдера | Импортозамещение / 152-ФЗ |

**Боеспособные варианты размещения:**

| Вариант | Стоимость | Готовность | Когда брать |
|---|---|---|---|
| Виртуалка от ИТ-службы НГУ | 0 ₽ | 1–3 дня | Первый кандидат, если есть VMware/Proxmox |
| Мини-ПК Beelink/MinisForum N100 + Ubuntu Server | 18–25 тыс. ₽ разово | 2 дня | Если нет виртуалки и есть бюджет на железо |
| VPS у Selectel / Timeweb / SberCloud | 300–800 ₽/мес | 30 минут | Без капекса, но нужен надёжный сервер |
| Railway (текущая площадка) | $5–20/мес | Уже работает | Для быстрого старта; миграция — по сценарию ИУ.001 §6.7 |

**Сравнение «соседей по серверу» (LEYKA не помешает работе):**

LEYKA = ≈250 МБ RAM, ≈2 ГБ диска, 1 порт. Это **меньше любого мало-мальского веб-сервиса** — даже легче чем Postgres-инстанс или Java-приложение. Если ИТ-служба скажет «места нет» — значит сервер уже перегружен и LEYKA — последний из сервисов, который должен это спровоцировать; нужен другой сервер.

**Чек-лист для разговора с ИТ-службой НГУ:**

- [ ] Подтверждена возможность выделить 512 МБ RAM, 2 vCPU, 5 ГБ диска;
- [ ] Назван путь для БД (например, `/var/lib/leyka/`) с правом на запись для технологического пользователя;
- [ ] Открыт TCP-порт (например, 8000) для uvicorn — внутренний;
- [ ] Настроен nginx-reverse-proxy на этой же машине с HTTPS (Let's Encrypt или корпоративный CA);
- [ ] Согласовано хранилище для бэкапов (Я.Диск через `rclone`, S3-совместимое, NAS);
- [ ] Назначен ответственный со стороны ИТ (правит Linux-обновления, перезагрузки);
- [ ] Согласован SLA (рекомендация: «работа в рабочее время; downtime ≤ 4 часов на восстановление»).

После заполнения чек-листа — установка по разделу 6 руководства `LEYKA_InstallManual_GOST19.md`.
