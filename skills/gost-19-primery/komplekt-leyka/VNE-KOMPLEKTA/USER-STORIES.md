## 1. Назначение документа

### 1.1 Цель

Зафиксировать **функциональные требования** системы LEYKA в формате
пользовательских историй, чтобы:

- 🎯 продакт-менеджер видел, **что уже сделано** и **что в очереди**;
- 🛠 разработчик понимал **бизнес-смысл** каждой реализованной фичи;
- 📋 заказчик мог **трассировать** свои потребности на конкретный функционал;
- 🧪 QA-специалист имел **критерии приёмки** для регресс-тестов.

### 1.2 Скоп системы

LEYKA — внутренний инструмент ЦИИ НГУ для:

- ведения **проектов с заказчиками** (МТС, Альфа-Банк, грантодатели Минобрнауки);
- учёта **обязательств центра** по 11 KPI Минобрнауки (Приложение №2);
- организации **командной работы** через канбан с RBAC;
- **онбординга новых сотрудников** через цепочку приглашений.

## 2. Методология

### 2.1 Формат пользовательской истории

Используется классический шаблон **Connextra** (Mike Cohn, *User Stories Applied*):

```
КАК <персона>,
Я ХОЧУ <функция>,
ЧТОБЫ <бизнес-выгода>.
```

К каждой истории — **критерии приёмки** в формате Gherkin (BDD):

```
Дано <предусловие>,
Когда <действие пользователя>,
Тогда <ожидаемый результат>.
```

### 2.2 Приоритизация — MoSCoW

| Уровень       | Описание                                                        |
|---------------|-----------------------------------------------------------------|
| **Must**      | Без этого продукт не функционирует                              |
| **Should**    | Важно, но релиз без этого возможен                              |
| **Could**     | Желательно, добавит ценности                                    |
| **Won't**     | Сознательно вне текущего скоупа                                 |

### 2.3 Оценка сложности

Story points по Фибоначчи: **1, 2, 3, 5, 8, 13, 21**.
Эпики оцениваются как сумма входящих историй.

### 2.4 Definition of Done

История считается завершённой, если:

1. ✅ Реализован backend-эндпоинт (если применимо).
2. ✅ Реализован frontend-компонент.
3. ✅ Покрыт минимум одним регресс-тестом (для backend).
4. ✅ TypeScript-компиляция без ошибок.
5. ✅ Smoke-проверка в браузере прошла.
6. ✅ Документация обновлена ([README.md](README.md), [ARC.md](ARC.md)).

### Эпик A: Аутентификация и онбординг (12 историй)

#### US-A01 · Вход через Mail.ru OAuth · `Must`

> **КАК** сотрудник центра с почтой на Mail.ru,
> **Я ХОЧУ** войти в систему одним кликом без регистрации,
> **ЧТОБЫ** не запоминать ещё один пароль.

**Критерии приёмки:**
- **Дано** я открыл `leyka-nsu.vercel.app`,
- **Когда** я нажимаю «Войти через Mail.ru»,
- **Тогда** меня редиректит на oauth.mail.ru, после согласия я возвращаюсь в систему авторизованным.

**Технические детали:** OAuth 2.0 с CSRF state-cookie, JWT в HttpOnly cookie.

---

#### US-A02 · Вход через Google OAuth · `Must`

> **КАК** сотрудник с корпоративным Google-аккаунтом,
> **Я ХОЧУ** войти через Google,
> **ЧТОБЫ** использовать единый ID для рабочих сервисов.

**Критерии приёмки:** аналогично US-A01 для google.com.

---

#### US-A03 · Резервный вход по логину/паролю · `Should`

> **КАК** администратор системы,
> **Я ХОЧУ** иметь «root»-вход по email и паролю,
> **ЧТОБЫ** не остаться без доступа, если OAuth-провайдер сломается.

**Критерии приёмки:**
- **Дано** в окружении заданы `ROOT_EMAIL` и `ROOT_PASSWORD`,
- **Когда** я ввожу их на login-экране,
- **Тогда** я авторизуюсь как `is_superuser=true`.

---

#### US-A04 · Сессия живёт неделю · `Should`

> **КАК** ежедневный пользователь,
> **Я ХОЧУ** не логиниться при каждом открытии вкладки,
> **ЧТОБЫ** не отвлекаться от работы.

**Критерии приёмки:** JWT TTL = 168 часов, cookie HttpOnly+Secure+SameSite=Lax.

---

#### US-A05 · Выход из системы · `Must`

> **КАК** пользователь на общем компьютере,
> **Я ХОЧУ** иметь кнопку «Выйти»,
> **ЧТОБЫ** следующий пользователь не работал под моим именем.

**Критерии приёмки:** клик в дропдауне профиля → cookie стирается → редирект на login.

---

#### US-A06 · Изменение собственного имени в профиле · `Should`

> **КАК** пользователь, у которого OAuth-провайдер прислал странное имя (например `bububu123`),
> **Я ХОЧУ** один раз поправить имя в профиле,
> **ЧТОБЫ** коллеги видели меня нормально в @-упоминаниях и комментариях.

**Критерии приёмки:**
- **Дано** я открыл «Настройки профиля»,
- **Когда** я меняю поле «Как меня видят коллеги» и нажимаю «Сохранить»,
- **Тогда** новое имя видно во всех местах: шапка, чат, мысленные упоминания.

---

#### US-A07 · Запрет на сброс прав последнего админа · `Must`

> **КАК** единственный активный администратор,
> **Я ХОЧУ** видеть ошибку при попытке снять с себя `is_superuser`,
> **ЧТОБЫ** не оставить систему без администратора.

**Критерии приёмки:**
- **Дано** я единственный активный admin,
- **Когда** я пытаюсь PATCH `/users/{me}` с `is_superuser=false`,
- **Тогда** возвращается 400 с пояснением «Нельзя оставить систему без администратора».

---

#### US-A08 · Запрет на удаление самого себя · `Must`

> **КАК** администратор,
> **Я ХОЧУ** не иметь возможности удалить свой собственный аккаунт,
> **ЧТОБЫ** случайным кликом не выпасть из системы навсегда.

**Критерии приёмки:** DELETE `/users/{me}` → 400.

---

#### US-A09 · Дружелюбный экран при отмене OAuth · `Should`

> **КАК** пользователь, передумавший входить через Mail.ru,
> **Я ХОЧУ** вернуться на экран входа с понятным сообщением,
> **ЧТОБЫ** не видеть сырое JSON «Field required: code».

**Критерии приёмки:**
- **Дано** на странице Mail.ru я нажал «Отмена»,
- **Когда** провайдер делает callback с `?error=access_denied`,
- **Тогда** я вижу login-экран с жёлтой плашкой «Вход через Mail.ru не выполнен».

---

#### US-A10 · Брендированный экран загрузки · `Could`

> **КАК** пользователь, открывающий приложение после релиза,
> **Я ХОЧУ** видеть фирменный лоадер вместо серого «Загружаю…»,
> **ЧТОБЫ** понимать, что система действительно работает.

**Критерии приёмки:** карточка с бегущими каплями + полосой прогресса + текстом «Поливаем задачи…».

---

#### US-A11 · Empty-state для гостя без проектов · `Should`

> **КАК** новый сотрудник, вошедший без приглашения,
> **Я ХОЧУ** увидеть инструкцию, что делать дальше,
> **ЧТОБЫ** не тыкаться в пустой интерфейс.

**Критерии приёмки:**
- **Дано** я не superuser и не состою ни в одном проекте,
- **Когда** я попадаю на главный экран,
- **Тогда** вижу: «Если у тебя есть ссылка-приглашение — открой её / Иначе напиши админу [mailto: ROOT_EMAIL]».

---

#### US-A12 · Поделиться идеей с разработчиком · `Could`

> **КАК** пользователь системы,
> **Я ХОЧУ** одним кликом отправить идею или баг разработчику,
> **ЧТОБЫ** улучшить продукт без долгого поиска контактов.

**Критерии приёмки:** в дропдауне профиля кнопка «💡 Поделись идеей с разработчиком» открывает почтовый клиент с предзаполненным `mailto:user@example.com?subject=Идея для LEYKA`.

---

- 10 backend-тестов: RBAC, self-merge, lockout-защита, перенос данных, конфликт ролей, дедупликация лайков, логин по обоим email после merge.

### Эпик L: Резервное копирование и сохранность данных (4 истории)

#### US-L01 · Скачать резервную копию БД одной кнопкой · `Must`

> **КАК** менеджер проекта или администратор центра,
> **Я ХОЧУ** одной кнопкой скачать ZIP-архив со снимком БД,
> **ЧТОБЫ** хранить страховку у себя — если сервис упадёт или потребуется переезд, данные не теряются.

**Критерии приёмки:**
- В меню профиля (правый верхний угол) пункт «Резервная копия» виден тем, у кого `is_superuser` ИЛИ membership с `can_edit_project` хотя бы в одном проекте;
- Клик открывает модалку с двумя секциями: «Скачать» (всегда доступно, кому виден пункт) и «Восстановить» (только для admin);
- Кнопка «Скачать сейчас» вызывает `GET /api/v1/backup/export`, ответ — ZIP с filename `leyka-backup-YYYY-MM-DD-HHMM.zip` через `Content-Disposition`;
- Внутри ZIP: `leyka.db` (атомарный bytes-снимок через нативный SQLite Connection.backup, не блокирует живые транзакции) + `manifest.json` (формат, версия приложения, дата UTC, counts по основным таблицам);
- Файл сохраняется в загрузках браузера через невидимый `<a download>`;
- Visual-feedback после успеха: «✓ Файл сохранён в загрузках браузера».

**Защиты:**
- Outsider (не менеджер) — 403 с понятным сообщением;
- Unauthenticated — 401;
- На in-memory БД (тесты) — 503 «не поддерживается».

---

#### US-L02 · Восстановить БД из архива · `Must`

> **КАК** администратор,
> **Я ХОЧУ** загрузить ранее скачанный ZIP-архив и восстановить из него БД,
> **ЧТОБЫ** вернуть систему к состоянию на момент бэкапа после сбоя или после переезда на новый сервер.

**Критерии приёмки:**
- Секция «Восстановить из файла» видна только администратору;
- File picker `.zip` → нажатие «Восстановить» → native confirm с предупреждением «Заменить текущую БД? Все изменения после момента бэкапа будут потеряны»;
- Backend валидирует ZIP: должен быть `leyka.db` + `manifest.json`, leyka.db должен начинаться с заголовка `SQLite format 3\x00` (защита от случайной заливки чужого файла);
- Перед заменой `engine.dispose()` закрывает connection pool, старая БД переименовывается в `leyka.db.before-restore` (страховка от отката), новая записывается, WAL/SHM-хвосты от старой БД удаляются;
- Response содержит manifest нового бэкапа (для сверки) + предупреждение «Перезапусти сервис».

**Защита:**
- Только `superuser`, иначе 403;
- Round-trip покрыт e2e-тестом: создать данные → export → DELETE → import → данные восстановились (через отдельную fixture с file-based engine).

---

#### US-L03 · Откат от отката · `Should`

> **КАК** администратор, который ошибся файлом при восстановлении,
> **Я ХОЧУ** откатить «откат» обратно к состоянию до восстановления,
> **ЧТОБЫ** не объяснять пользователям, почему их данные за последний месяц пропали.

**Критерии приёмки:**
- При каждом восстановлении старый файл `leyka.db` сохраняется как `leyka.db.before-restore` в той же папке (на Railway — `/data/`, на сервере НГУ — `/var/lib/leyka/`, локально — `./backend/`);
- В UI после успешного restore показывается имя файла-страховки;
- В `LEYKA_InstallManual_GOST19.md` §6.7 описана пошаговая процедура отката через переименование файлов и `systemctl restart`.

**Технические детали:** хранится только последняя версия (перезаписывается при следующем restore). Для исторической глубины используется отдельный systemd-таймер `leyka-backup.timer` с rolling 7+4 (см. §6.4 InstallManual).

---

#### US-L04 · Сценарий переезда Railway → сервер ЦИИ НГУ · `Could`

> **КАК** администратор,
> **Я ХОЧУ** перенести систему с Railway на физический сервер ЦИИ НГУ без потери данных,
> **ЧТОБЫ** обеспечить импортозамещение и аудиторские требования по локализации данных.

**Критерии приёмки (документация):**
- В `LEYKA_InstallManual_GOST19.md` §6.7 описана 6-шаговая процедура: скачать backup → развернуть на НГУ-сервере → подготовить admin-вход через `set_root_password` → restore через UI → перезапуск сервиса → проверка;
- В `LEYKA_UserManual_GOST19.md` §3.13 — пользовательская версия процедуры;
- Явно описано, что cookies сессий перестанут работать (новый JWT_SECRET) — пользователи проходят аутентификацию заново;
- Описан откат от отката (см. US-L03).

## 7. Технический долг и риски

### 7.1 Технический долг

| Долг                                       | Влияние                              | План решения        |
|--------------------------------------------|--------------------------------------|---------------------|
| Нет E2E-тестов                             | Регрессии ловит ручной smoke         | Playwright в Q3     |
| TanStack Query refetch везде 15s           | Лишний трафик                        | Тонкая настройка по экранам |
| Bundle не code-split                       | First-load 250KB                     | Route-based split   |
| SQLite без `PRAGMA foreign_keys=ON`        | FK enforcement только через ORM      | Включить + протестировать |
| Нет логирования латентности                | Сложно искать медленные запросы      | US-X08              |
| Дубли проектов в проде                     | Визуальный мусор в сайдбаре          | US-X19              |
| Дубли юзеров (user@example.com / @gmail)   | Путаница, кто залогинен              | US-X02              |

### 7.2 Риски

| Риск                                   | Вероятность | Влияние | Митигация                                     |
|----------------------------------------|:----------:|:-------:|-----------------------------------------------|

| starlette CVE-2025-62727 (FileResponse)| Принят    | Низкое  | Не используем FileResponse, документировано    |
