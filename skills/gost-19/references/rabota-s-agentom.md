# Как вести комплект вместе с языковым агентом

Комплект ЕСПД — редкий случай, где агент по-настоящему полезен: объём большой,
строй документов повторяемый, а ошибки — механические. И тот же случай, где агент
вредит тише всего: документ, написанный красиво и не соответствующий изделию, проходит
глазами и не проходит приёмку.

Ниже — разделение труда, проверенное на комплекте из одиннадцати документов.

## Что поручать агенту

| Поручение | Почему ему |
|---|---|
| **Строй документа по стандарту** — разделы, их порядок, аннотация, содержание | механическая работа, память стандарта |
| **Перенос замеров в текст** — взять число из вывода команды и вписать с указанием команды | ровно то, где человек ошибается чаще |
| **Сверка между документами** — одно и то же число в трёх документах | человек этого не видит |
| **Опись состава, таблицы объёмов, контрольные суммы** | это вообще не письмо, а счёт (см. `gost-19-sverka`) |
| **Переписать абзац под читателя** — из руководства программиста в руководство оператора | смена регистра речи |
| **Написать проверку-сторож** к числу в документе | лучший способ закрепить |

## Чего не поручать никогда

* **не поручать выдумывать числа.** Формулировка «оцени примерный объём» гарантирует
  красивое неверное число. Правильно: «выполни команду, возьми число из вывода, впиши
  вместе с командой и датой»;
* **не поручать описывать то, чего агент не видел.** Раздел об алгоритме пишется
  по коду, открытому в этой же сессии, а не по названию модуля;
* **не поручать обещания.** «Планируется реализовать», «в дальнейшем будет» в документе
  ЕСПД — след того, что документ писали без изделия;
* **не поручать оценку соответствия требованию.** Ответ «требование закрыто» обязан
  подкрепляться прогоном, испытанием или ссылкой на раздел, а не мнением.

## Промпты, которые работают

Три формы, дающие проверяемый результат.

**Замер вместо оценки:**

> Нужна таблица объёма исходного текста для раздела 1 «Текста программы». Посчитай
> строки по языкам и каталогам командой, приведи саму команду и дату замера, исключи
> каталоги с входными данными заказчика. Числа, которых не получилось посчитать, назови
> непосчитанными — не оценивай.

**Документ по образцу:**

> Напиши раздел 3 руководства оператора по образцу `gost-19-primery/komplekt-arhi/…-34…`:
> тот же строй, тот же регистр речи (от лица человека, который получил сообщение),
> те же таблицы состояний. Содержание бери только из кода и страниц изделия;
> чего в изделии нет — не описывай, а выпиши отдельным списком «не реализовано».

**Проверка на честность (лучший из трёх):**

> Пройди по документу и найди утверждения, которые нельзя проверить по репозиторию:
> числа без команды, «поддерживается» без ссылки на код, «протестировано» без набора
> проверок. Ничего не исправляй — выпиши список с номерами строк.

Последний промпт стоит запускать перед каждой сдачей. Он находит то, что человек уже
перестал видеть.

## Систематические ошибки агента — и чем их ловить

| Ошибка | Как выглядит | Сторож |
|---|---|---|
| **Число из головы** | «около 25 тысяч строк», «более 700 проверок» | проверка, сверяющая число в документе с прогоном (`gost-19-sverka`) |
| **Тихое устаревание** | число было верным неделю назад | та же проверка; сверка обязана быть в наборе, а не в памяти |
| **Разъехавшийся комплект** | в ПМИ 784 проверки, в README 792 | одно число — один источник; остальные документы ссылаются |
| **Пересказ стандарта** | раздел «Назначение» о том, что бывают программы | вычитка человеком: пересказ виден сразу |
| **Придуманный пункт стандарта** | ссылка на несуществующий пункт ГОСТа | сверка по тексту стандарта; ссылки на пункты проверять руками |
| **Разметка, которая печатается** | комментарии HTML, попавшие в текст документа | проверка, запрещающая служебную разметку в исходном тексте |
| **Будущее время** | «будет реализовано» | поиск по словам «планируется», «будет», «предполагается» |

## Разделение по времени: когда агент, когда человек

1. **До написания** — человек: решает состав комплекта, обозначения, что сдаётся.
   Это договорные вопросы, агент их не знает.
2. **Во время** — агент: строй, замеры, таблицы, сверки, черновики разделов.
   Человек читает каждый раздел сразу, а не в конце.
3. **Перед сдачей** — оба: агент гонит проверки честности и сверку чисел, человек
   читает документ целиком **вслух по диагонали**. Абзац, который трудно прочесть
   вслух, почти всегда написан без понимания.
4. **После замечаний приёмки** — человек формулирует, что именно не устроило, агент
   правит и **добавляет сторожа**, чтобы это замечание не вернулось.

## Как хранить документы, чтобы агент был полезен

**[практика]** Держите документы **в репозитории изделия, рядом с кодом, в Markdown.**

Причины:

* документ и код правятся одним изменением — иначе они расходятся в первый же день;
* правки документов видны в истории и проходят ревью так же, как код;
* агент читает и документ, и код в одной сессии — только тогда он может сверить одно
  с другим;
* числа в документах становятся проверяемыми: проверка открывает документ, открывает
  диск и сравнивает (см. `gost-19-sverka`).

Отдельно лежащий `.docx` в общей папке ломает всё четыре пункта сразу. Если заказчику
нужен `.docx` или бумага — это **вывод** из исходного текста, а не место хранения;
маршруты вывода описаны в `gost-19-pechat`.
