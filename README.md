# Навыки для агента: документация по ЕСПД и рабочий порядок SKICODING

Два семейства навыков в одном пакете. Первое учит агента **писать комплект программной
документации по ГОСТ 19 (ЕСПД)** так, чтобы его приняли. Второе — **SKICODING** — задаёт
порядок работы, при котором этот комплект не приходится писать в конце: код, документы
и бэклог двигаются одним шагом, а агент не выдумывает за программиста, а спрашивает.

Вместе они отвечают на два разных вопроса:

| | Вопрос | Семейство |
|---|---|---|
| **Что писать** | из чего состоит комплект, что внутри каждого документа, как его оформить и сдать | `gost-19*` |
| **Когда и в каком порядке** | когда трогать документы, куда девать отложенное, где живут решения, как узнать, что ожидалось | `skicoding` |

**Главное правило пакета:**

> Каждое число в документе несёт команду, которой оно получено; каждое решение — обстоятельство,
> которое его потребовало; каждое требование — испытание, которым оно закрыто.
> Всё остальное — оформление.

## Навыки

| Навык | О чём |
|---|---|

| `gost-19` | Хаб ЕСПД: карта стандартов, коды видов документов, обозначения и редакции, работа с агентом |

| `gost-19-dokumenty` | Что кладётся внутрь каждого вида: ТЗ, ПЗ, описание программы, текст программы, руководства, спецификация |
| `gost-19-sverka` | Числа, сверяемые с диском: опись, контрольные суммы, десять проверок-сторожей, ритуал сдачи |

## Порядок работы, который навыки будут рекомендовать

Это не пожелание, а то, что агент начнёт предлагать после установки. Полезно знать
заранее — чтобы понимать, почему он спрашивает, вместо того чтобы сразу писать код.

### Режим 1. Проект в разработке — текст и код через один

**Ски-кодинг**: текстовые и кодовые шаги чередуются, как лыжные следы, — левая, правая,
левая, правая. Каждый шаг оставляет проверяемый артефакт (документ, коммит, проверку),
который можно показать пальцем и сверить с предыдущим. Итерация — шесть шагов:

| Шаг | | Что |
|---|---|---|
| 1 | текст | **разбор**: что есть, чего не хватает, что закрываем, что откладываем |
| 2 | код | **реализация фаз** — по одному пункту разбора за фазу |
| 3 | текст | **актуализация документов**, которых коснулись фазы |
| 4 | код | **то, что выросло из шага 3** — чаще всего интерфейс |
| 5 | текст | **бэклог** отложенного |
| 6 | код | **проверки** — по одной на фазу |

Несущее правило: **разбор пишется до правок кода.** Нашли по дороге ошибку — записали
строкой в таблицу и не пошли чинить.

Внутри обычной задачи на день тот же порядок сжимается до семи действий:

1. **Спросить, что ожидается** — короткое интервью, если задача не очевидна;
2. **Записать сценарий** использования с номером → `docs/USE-CASES.md`;
3. **Принять и записать решение**, если есть развилка — в день принятия;
4. **Код и проверка вместе** — проверка это будущее доказательство на приёмке;
5. **Обновить документы, которых коснулись** — один-два, не весь комплект;
6. **Записать отложенное** с причиной и признаком «когда пора» → `docs/BEKLOG.md`;
7. **Перемерить числа**, если менялся объём.

**Шаг не закончен, пока не сделаны пункты 5–7.** «Допишем документы потом» означает
«не напишем»: через неделю автор не помнит обстоятельств.

Паттерн держит проект между двумя капканами: **гонка кода** — через неделю пять
несовместимых решений и никто не помнит почему; **паралич документов** — четыре тысячи
строк текста, в коде ничего, текст устарел. Каждый текстовый шаг кончается списком
конкретных правок, каждый кодовый — актуализацией текста.

Комплект при этом **не пишется разом**. Документы заводятся рано и растут: пояснительная
записка — в первый день (в ней сразу разделы «Решения» и «Чего изделие не делает»),
описание программы — когда появился алгоритм, руководства — когда есть чем пользоваться,
программа испытаний — когда есть что испытывать, опись и спецификация — в конце.

### Режим 2. Проект готов, документов нет

Комплект восстанавливается **по одному документу за проход**, и первым идёт не документ,
а интервью:

```
инвентаризация → интервью (что ожидалось) → сценарии → техническое задание →
описание программы → интервью о решениях → пояснительная записка → руководства →
программа и методика испытаний → текст программы (опись) → спецификация
```

Между проходами — чтение человеком. Причина жёсткого порядка: по коду восстанавливается
«что программа делает», но не «что ожидалось», — а принимают работу по ожиданиям.
Ошибка в первом документе размножится по всем остальным: они ссылаются друг на друга.

### Почему интервью

Агент, пишущий документацию по коду молча, отвечает на вопрос «что делает программа».
Получается пересказ кода: «модуль читает данные из внешней системы и сохраняет в базу».

После интервью получается документ: «изделие снимает состояние стройки раз в час,
потому что до него числа обновлялись на еженедельном совещании, и решения принимались
по данным недельной давности».

Отсюда правило: **без сценариев использования непонятно, что ожидалось по заданию
и что проверять в программе испытаний.** Сценарий — узел, из которого выводятся
и требование, и испытание:

```
интервью → сценарий → требование задания (4.х) → испытание (И-х) → строка в ведомости покрытия
```

Как ведётся интервью: по одному вопросу за раз, с вариантами ответа, не больше
семи-девяти вопросов за круг, ответы сразу в файл. «Не знаю» — законный ответ:
он записывается как «не выяснено» и превращается в вопрос заказчику, а не в догадку.

### Куда что пишется

| Что | Где |
|---|---|
| Сценарии использования | `docs/USE-CASES.md` |
| Отложенное | `docs/BEKLOG.md` — рядом с кодом, правится тем же коммитом, видно агенту и на ревью |
| Решения по архитектуре | раздел «Решения» пояснительной записки; черновая запись — в день принятия |
| Ограничения — чего изделие не делает | раздел пояснительной записки, пишется **в первый день** |
| Невыполненные требования задания | ведомость покрытия + раздел об отступлениях + раздел состояния функций в ПМИ |

Про бэклог отдельно: он **не план работ**, а память об отложенном. У каждой записи —
повод, что именно, почему не сейчас, что будет если не делать, и **признак, что пора**.
Без последнего поля бэклог за полгода превращается в свалку.

Про ограничения отдельно: **объявленное заранее — решение, объявленное в конце —
оправдание.** Разница видна на приёмке невооружённым глазом.

### Как это соотносится с spec-driven development

Ски-кодинг — родственник подходов, которые с 2025 года называют **разработкой
по спецификации**: GitHub Spec Kit, OpenSpec, Kiro, BMAD. Замысел общий — не давать
агенту писать код с голоса. Из них взяты шаблоны требований **EARS**, правило
«в спецификации нет реализации», ограничение на число открытых вопросов и порядок
их важности, дельта-правки с пометками «добавлено / изменено / удалено» и файл
принципов, который агент читает каждую сессию.

Главная претензия к этому семейству — **текст расходится с кодом за дни, и ни одно
средство не отвечает на это ничем, кроме слова «дисциплина»**. Наш ответ конкретный:
проверки-сторожа, которые роняют прогон при расхождении документа с диском, и признак
законченности фазы, в который входит обновлённый документ. Подробный разбор — в навыке
`skicoding`, справка `spec-driven-sosedi.md`.

## Установка

```bash
git clone <адрес-репозитория> gost-19-skills
cd gost-19-skills
```

**macOS / Linux:**
```bash
chmod +x install.sh && ./install.sh
```

**Windows (PowerShell):**
```powershell
./install.ps1
```

Затем **перезапустите Claude Code / Codex**, чтобы он подхватил навыки.

Установщик делает ссылки (симлинки на Unix, junction-каталоги на Windows), а не копии, —
поэтому `git pull` обновляет навыки сразу у всех агентов на машине. Навык, чьё имя
в целевом каталоге уже занято, **пропускается**: чужое не затирается.

**Вручную:** скопируйте каталоги из `skills/` в `~/.claude/skills/` (Claude Code)
и/или `~/.agents/skills/` (Codex). Сборки нет — навык это папка с файлом `SKILL.md`.

> Устройство репозитория и сценарии установки повторяют пакет **apple-design-skills**
> (MIT): раскладка `skills/<имя>/SKILL.md` плюс `references/`, установка ссылками
> сразу в два каталога агентов.

## Как проверить, что установилось

Четыре проверки, по возрастанию убедительности. Первые три — минута.

**1. Ссылки на месте и ведут в репозиторий:**

```bash
ls -l ~/.claude/skills | grep gost-19        # восемь строк со стрелками → …/gost-19-skills/skills/…
ls -l ~/.agents/skills | grep skicoding      # если пользуетесь Codex
```

Симлинк, ведущий «в никуда» (красный в выводе `ls`), означает, что репозиторий
переехал: переустановите.

**2. Навык читается целиком:**

```bash
head -5 ~/.claude/skills/gost-19/SKILL.md    # шапка с name и description
ls ~/.claude/skills/gost-19-primery/komplekt-arhi | wc -l   # 12
```

**3. Агент видит навык.** Перезапустите Claude Code и спросите прямо:

> Какие навыки про ГОСТ 19 тебе доступны? Перечисли имена и скажи, для чего каждый.

Ответ обязан назвать восемь имён. Если названо меньше — агент не перечитал каталог
навыков: перезапустите ещё раз.

**4. Навык срабатывает сам.** Это главная проверка: навык полезен не тогда, когда
его видно в списке, а когда агент берёт его **без напоминания**. Задайте вопрос,
не называя навыков:

> Мне нужно написать руководство оператора по ГОСТ 19.505-79 для нашего сервиса.
> С чего начать?

Признаки, что сработало: агент называет разделы по стандарту, предлагает посмотреть
образец, **задаёт вопросы о том, что ожидалось**, и не начинает писать текст сразу.
Если вместо этого пошёл сочинять документ — навык не подхватился либо его описание
не совпало с вашей формулировкой; скажите «используй навык `gost-19-dokumenty`»
и посмотрите, изменится ли ответ.

**Проверка самого репозитория** (если правите навыки): ссылки между справками должны
сходиться — каждый файл, упомянутый в тексте, существует. Быстрый способ:

```bash
cd ~/gost-19-skills
grep -rhoE '`[a-z0-9-]+/references/[a-z0-9-]+\.md`' skills | tr -d '`' | sort -u | \
  while read p; do [ -f "skills/$p" ] || echo "нет файла: $p"; done
```

Пустой вывод — всё сходится.

## Как начать

**Новый проект:** скажите агенту «работаем по skicoding» — он проведёт первый круг
интервью, заведёт `docs/USE-CASES.md`, `docs/BEKLOG.md` и пояснительную записку
с разделами решений и ограничений, и дальше будет держать шаг.

**Готовый проект без документов:** «собери комплект по ГОСТ 19, режим готового проекта» —
агент начнёт с инвентаризации и интервью, а не с письма.

**Один документ:** «напиши руководство оператора по ГОСТ 19.505-79» — агент возьмёт
строй из `gost-19-dokumenty`, образец из `gost-19-primery` и спросит недостающее.

## Соглашение о пометках

У каждого нетривиального утверждения в навыках стоит его происхождение. Это не
оформление: разница между буквой стандарта и чьим-то решением — первое, что спрашивают
на нормоконтроле.

| Пометка | Что означает |
|---|---|
| **[ГОСТ]** | Требование стандарта; ссылка на пункт приведена |
| **[практика]** | Решение, которое стандарт не предписывает и не запрещает; приведён довод |
| **[замер]** | Проверено опытом, названы дата и условия; со временем может устареть |

Пометка **[замер]** особенно важна там, где речь о браузерах: поддержка постраничной
вёрстки меняется, и «этого нельзя» верно на дату замера, а не навсегда.

## Откуда это взялось

Навыки собраны на живой работе трёх проектов Центра искусственного интеллекта НГУ.

**Порядок работы** (ски-кодинг) сформулирован 23.05.2026 в проекте РАГРАФ — по факту
восьми с лишним итераций работы соло-разработчика с большой моделью. Здесь он обобщён
со стека одного проекта и дополнен режимом интервью и связкой с комплектом ЕСПД.

**Комплект документации** — одиннадцать документов ЕСПД к изделию для управления
строительными проектами (2026 год). Он писался вместе с изделием по тому же порядку,
печатался, проходил внутреннюю приёмку и правился по её замечаниям. Отсюда и перечень
граблей. В образцах он лежит двенадцатью файлами: задание представлено двумя
редакциями.

**Комплекты опубликованы целиком** — в навыке `gost-19-primery` их три, к трём разным
изделиям: платформа контроля регламентов (12 документов, два из них — две редакции
задания), фреймворк проверяемого управления (9 документов, включая редкий вид «описание
языка») и небольшое веб-изделие (6 документов с другой схемой обозначений и с
пользовательскими историями).

**Все они обезличены.** Сняты титульные части с листами утверждения, наименования
сторон, должности и фамилии — включая графы правообладателя и владельца документа,
вместо них роли, — номера договоров, адреса площадок, списки научных статей. Разделы,
требования и формулировки оставлены как в подлиннике. Упоминания ЦИИ НГУ оставлены:
это разработчик, а не сторона, чьи данные требуется скрыть. Персональных данных,
доступов и сведений о третьих лицах не осталось — проверено поиском перед публикацией.

Примеры внутри самих навыков построены на условном обозначении `АБВГ.00001-01`,
чтобы их можно было переносить на свой проект не задумываясь.

**Текстов ГОСТов здесь нет.** Стандарты распространяются своим порядком; навыки
их не воспроизводят, а ссылаются на пункты. Перед сдачей комплекта сверяйтесь
с действующей редакцией стандарта.

## Чего эти навыки не делают

* **не заменяют нормоконтроль.** Они доводят комплект до состояния, в котором
  нормоконтролёру есть что проверять;
* **не пишут документ за вас целиком.** Документ, сгенерированный без замеров
  и без изделия под рукой, читается как реферат и отклоняется первым;
* **не заменяют доску задач и спринты.** SKICODING добавляет к ним одно правило
  о границах шага — и ни на что больше не покушается;
* **не покрывают ГОСТ 34 и ГОСТ 2.** ЕСПД (серия 19) — про программные изделия;
  автоматизированные системы (серия 34) и конструкторская документация (серия 2)
  устроены иначе.

## English summary

Two skill families in one package.

**`gost-19*` (seven skills)** — producing a **GOST 19 / ESPD** software-documentation
set (the Russian software documentation standard family, still mandatory for
state-funded and many enterprise projects in Russia and the CIS): the map of the
standards and document-type codes, designations and editions, what belongs inside each
document, making every number verifiable against the repository (inventories, checksums,
guard tests, a pre-delivery ritual), typesetting and printing to PDF (what CSS Paged
Media can and cannot do in browsers as of late 2026, and the docx route), and the
test-programme / traceability side of acceptance. Includes **three complete real
document sets** (27 documents, anonymised) as worked examples.

**`skicoding` (one skill)** — the working order that keeps code, documents and backlog
in step: text and code steps alternating like ski tracks (analysis before any code
change, phases, backlog, decisions, constraints), where the backlog lives, how
architecture decisions and project constraints are recorded, and an **interview mode** — the agent asks the
programmer what was *expected* (code only shows what the program *does*) and turns the
answers into use cases, which then drive both the requirements and the acceptance tests.
Two modes: incremental (project in development) and retrofit (working project, no docs).
It also maps the family against **spec-driven development** (Spec Kit, OpenSpec, Kiro,
BMAD): what is borrowed — EARS requirement patterns among others — and what answers
the standing criticism that specs drift away from code within days.

The material is in **Russian**, because GOST 19 is a Russian-language standard family
and so is every document produced under it. Skill descriptions carry English keywords
so an agent routes correctly regardless of the prompt language.
